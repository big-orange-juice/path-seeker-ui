# 跟随车夫：趣事连续播放与锁屏停顿诊断

诊断版本：`tour-audio-continuity-20261112`。接续全路线预缓存改动。

现场日志到达后的后续结论与修复见 [息屏定位、跟随生命周期与酒店首站修复](alipay-follow-lifecycle-2026-11-12.md)。该版本修复游客消息连接断开误关跟随及后开启跟随遗漏预加载，并提供车夫 APP 0.3.5；下文“尚不能确认”描述的是收到现场日志之前的分析阶段。

## 现场现象与边界

同一段趣事中途停住，恢复后接着原话；车夫没有开启麦克风。偶尔靠近节点时亮屏，随后听到节点讲解。

到站不会清空共享内存缓存、磁盘缓存或趣事续播位置。正在播的趣事已完整解码到内存，单纯“下一段尚未下载”不能解释一句话中途停住。当前五段源素材按 `-45 dB`、最短 `0.5 秒` 检查静音，最长约 `0.883 秒`，未发现数秒静音；此检查不能排除手机、代理、网络或输出调度问题。结果为 `outputs/alipay-idle-audio/ceramics-silence-20261112.json`。

亮屏会恢复小程序前台状态刷新，现有逻辑检测到播放器失败、停滞或媒体连接断开时可能重连。因此“亮屏后听到节点”不等于服务端必须等游客亮屏才能判断到站。本轮没有现场停顿时的记录，尚不能确认中途停顿来自服务端输出、HTTP 传输还是支付宝后台播放器。

## 播放调度改动

1. 趣事持有当前段与下一段两个播放缓冲，当前段尚在播放时准备下一段。音频帧循环消费已就绪的缓冲，下载、磁盘读取和解码在独立任务运行，不等待定位及行程数据库轮询。
2. 到站入队、保存进度、准备首段节点音频期间继续当前趣事；节点首段可播放后再让出输出。节点结束后接着未完成趣事，不再因为队列刚出现节点就提前改成静音。
3. 一个节点已经开始后，章节之间准备音频时不插播趣事。现有节点顺序播放规则保留。
4. 下一段趣事不可用时尝试后续节目，全部不可用后退避 30 秒。仅配置一段时循环复用同一份音频数据。
5. 暂停、挂起和房间语音优先期间不推进趣事读取位置。到站切换不清除素材缓存，同一条媒体流持续输出。

双缓冲减少切换空档；首次素材准备尚未完成、全部素材失效、已开始节点的下一章节仍在等待等情况仍可能输出静音。已经发送到手机缓冲区的音频不能撤回，不能承诺零延迟或系统后台播放器永不暂停。

## 新增诊断

服务端 GET 会话状态新增 `transport`，小程序复制诊断会一并保存：

| 字段或事件 | 含义 |
| --- | --- |
| `lastWriteAt` | 最近一次 HTTP 写入及刷新完成时间；新连接初始化为连接时间 |
| `maximumWriteMilliseconds` | 本会话已完成 HTTP 写入及刷新的最大耗时 |
| `connected` / `disconnected` | 媒体连接建立及结束，包含媒体流 ID |
| `idle` / `route` / `room` / `silence` | 服务端输出类型变化 |
| 静音的 `reason` | 区分暂停、挂起、房间讲话、等待翻译、节点准备、趣事准备及等待到站 |
| `delivery` | 持续输出时每 30 秒保存一次 HTTP 写入完成记录 |
| `encoder-gap` | 获取下一份编码输出前已间隔至少 2 秒 |
| `write-backpressure` | 单次 HTTP 写入及刷新耗时至少 2 秒 |
| `transport-error` | 媒体输出异常类型 |

事件最多保留 64 条，同一会话重连后保留旧连接记录；服务端日志前缀为 `Tour audio output`。HTTP 写入完成不证明 Nginx 已转发到手机，更不证明手机实际出声。

小程序新增最多 12 条 `lifecycle`：`background` 为进入后台时状态，`foreground-before-refresh` 为亮屏后刷新及恢复前状态，`foreground-recovery` 为现有自动恢复前状态。包括原生播放位置、暂停及失败标志。`lastKnownServerStatus`、`lastKnownServerMediaSeconds` 是当时最近已收到的服务端快照，锁屏期间可能过时；需结合刷新后的 `server.transport` 与 `stageTimings`。记录不包含媒体票据和鉴权信息。关闭当前媒体会话后不能再从小程序复制其记录。

## 部署

1. 发布并重启现有 WebAPI，FFmpeg 仍用 `/usr/bin/ffmpeg`。保留 `App_Data/tour-audio` 或独立缓存目录的内容与读写权限，沿用已有趣事和预缓存配置。
2. 前端仓库运行 `pnpm --filter @path-seeker/mp-alipay build`，发布构建后的 `apps/mp-alipay/dist`。复制诊断的版本应为 `tour-audio-continuity-20261112`。
3. 无数据库迁移、不新增服务，也无新的 Nginx 配置要求；正式媒体路径原有关闭代理缓冲配置仍需有效。
4. 重启后游客重新加入房间、开启跟随。重新验证已完成节点时需结束旧行程再创建新行程。
5. 确认 `Tour audio preload completed startup-idle` 显示五段趣事成功，首轮出发前等待对应会话的路线预缓存完成，便于区分冷启动等待与锁屏问题。

仅发布后端即可获得调度修复；本轮测试应同时发布小程序以保存亮屏前证据。

## Android 与 iPhone 现场测试

两种系统分别记录机型、支付宝版本、网络类型和测试时间，先保持车夫麦克风关闭。

1. **远离所有节点**：开启跟随，确认趣事正常播放后锁屏听 5～10 分钟，跨过至少一次趣事切换，不通过反复亮屏维持播放。记录停顿时间及恢复后是否接着原话。
2. **停顿后保留记录**：允许亮屏回到小程序，页面刷新后立即复制诊断；先不要退出房间、关闭跟随或重启行程。新增记录会保存本次亮屏恢复前的状态，不要求在锁屏时操作。
3. **靠近节点**：新行程锁屏驶近节点并满足停留条件，观察趣事让出、节点播放及趣事续播。记录地点、停顿和亮屏时间，再复制诊断。
4. **优先级回归**：另做一次开麦、停止讲话、趣事恢复测试，再验证关闭跟随后可手动播放。

分析时对齐 `stageTimings.arrivedAt`、`audioStartedAt` 与 `lifecycle` 时间。到站已发生而节点首帧较晚，检查队列及素材准备；首帧早于亮屏而当时没声音，继续检查传输与播放器缓冲。服务端持续输出及 HTTP 写入记录不能单独证明是手机问题，需结合原生播放位置、重连、代理及网络情况。
