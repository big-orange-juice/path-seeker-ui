# 路线手动编辑的保存与吸附

## 重复保存导致顶点增长的原因

原实现把吸附后返回的密集折线作为编辑顶点，再在下一次保存时对每两个相邻顶点重新请求步行规划。规划输出又变成下一轮的输入，导致顶点、请求次数和失败连接数持续增长。保存按钮只限制请求进行中的点击，没有限制未修改路线的再次保存。

吸附结果提示中的连接数是相邻顶点之间的规划子段数，不是路线的站点路段数。

## 保存规则

- 已有几何且没有修改时，按钮显示“本段已保存”并禁用；状态层同样阻止重复提交。
- 缺少服务端几何的路段仍可首次保存站点之间的直线。
- 单段和批量保存共用请求锁；整个批量保存结束前禁止其他保存请求。
- 批量保存只提交有修改的路段，每段使用自己的顶点和最新几何版本。
- 保存失败时保留草稿；批量保存部分失败时，重试只提交尚未保存的路段。
- 后端校验版本和相邻站点后，对相同几何直接返回；不重新吸附、不写入、不增加几何版本、不撤销原有确认。
- 对真正修改的几何，后端复用原折线中没有变化的相邻连接；新增或移动顶点只规划受到影响的连接，删除顶点只规划合并后的新连接。
- 规划结果中的起终点固定为对应的编辑顶点，整段首尾固定到站点；未修改顶点直接保存原值，避免坐标系转换和数值转换产生漂移。
- 提示只统计本次实际重新规划的连接；存在吸附或校验提示时，弹窗提醒检查，不显示笼统的“操作成功”。

## 验证

前端：

```sh
node --test apps/web-admin/tests/routeMapEditor.test.mjs
pnpm --filter @path-seeker/web-admin typecheck
```

后端（在 CulturalTourism_System 仓库执行）：

```sh
dotnet test CulturalTourismSystem.ApiTests/CulturalTourismSystem.ApiTests.csproj --no-restore --filter "FullyQualifiedName~RouteMapSaveTests|FullyQualifiedName~RouteMapGenerationTests|FullyQualifiedName~RouteLineGeometryTests" -p:NuGetAudit=false
```

前端测试覆盖无修改重复保存、并发保存、批量保存各自几何、非当前路段保存、失败重试、批量部分失败和缺少几何的首次保存。后端测试覆盖密集规划结果的重复保存、局部改动的有限规划次数、插入和删除顶点、原始折线保存、吸附失败以及版本冲突，并同时验证 WGS84 和 GCJ-02 坐标系。

编辑器和手柄统一使用 WGS84，提交前转换为路线的存储坐标系；未修改的顶点复用原始存储坐标。站点入口改变后会保留相邻折线并标记待修复，重新打开编辑器时端点固定到新入口。更多同步、重排、确认及黄包车入口检查见 `route-map-flow-audit.md`。

修复需要更新前端和后端。已经保存的膨胀折线会被保留；如需清理，可重新生成指定路段后人工校核，也可手动删除多余顶点后保存。重新生成会覆盖该段已有人工路线。
