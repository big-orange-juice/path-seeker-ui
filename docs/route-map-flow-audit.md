# 路线地图流程检查与黄包车管理

检查范围为后台路线编排、站点同步和重排、地图加载、顶点编辑、单段和批量保存、自动生成、检查和确认，以及黄包车后台入口和既有服务接口。此次修改只作用于本地代码，没有部署或写入真实业务数据库。

## 已修复的问题

| 环节 | 原问题 | 修复后的行为 |
| --- | --- | --- |
| 重复保存 | 把吸附后的密集折线再次逐连接规划，顶点和请求数不断增长 | 未修改时前端禁止提交；后端同几何直接返回，只重新规划修改过的连接 |
| 单段与批量保存 | 并发请求及路段间共享编辑状态可能串线 | 全程保存锁；每段提交自己的顶点，使用最新几何版本；失败保留剩余草稿 |
| 撤销重做 | 历史跨路段共享，快照截断精度 | 每段维护独立历史，保留坐标精度，始终固定到当前站点入口 |
| 放弃草稿 | 缺少服务端几何时恢复成空数组 | 恢复两站端点，可继续编辑和首次保存 |
| 检查路线 | 检查会增加几何版本，前端响应覆盖未保存草稿 | 检查不写版本，前端合并响应并保留草稿 |
| 停靠资料 | 请求未提供坐标时，经纬度默认零；元数据更新删除相邻几何 | 经纬度改为可选且成对；仅修改文字时保留坐标、路段、版本及确认 |
| 移动站点 | 相邻路段被删除，坐标系可能混用；重开后端点无法修复 | 保留折线，标记相邻路段待修复；编辑坐标转入原存储坐标系；重开及撤销固定新端点 |
| 同步与重排 | 无变化也撤销确认；没有坐标的节点造成断号；顺序交换触发活动记录唯一索引冲突 | 无变化不写入；无坐标的新节点跳过；先腾出变化的编号，再更新和插入；相同站点对的几何保留 |
| 坐标系统一 | 不同文化点使用不同坐标系，路线一直无法确认 | 同步统一为路线存储坐标系，转换保留的几何，并校验端点 |
| 自动生成 | 重试重新规划已完成路段；非业务异常可能留下生成中状态 | 批量跳过已完成自动路段和已有人工路段；保留部分成功结果；失败退出生成中状态；单段覆盖人工路线必须明确确认 |
| 生成后的完整性 | 全部路段已有效时可能仍返回旧整线状态；单段成功提示没有说明其它段尚未完成 | 读取和生成返回前按当前路段重算整线状态；单段成功与整线就绪分别提示；校验列出具体段号、站点对和失败原因 |
| 网络与请求 | 没有超时的请求可能一直占用按钮；换路线后的晚响应覆盖新路线 | 加入请求超时和响应序号；编排重排的两次写入使用同一原路线 ID；不自动重试写请求 |
| 后端并发 | 不同请求实例同时通过版本检查 | 同一进程按路线分组串行处理，等待有上限；后来的旧版本保存返回冲突 |
| 旧几何损坏 | 解析旧数据失败，连检查或替换也无法进行 | 检查报告缺失或待修复，允许保存合法新几何替换 |
| 确认路线 | 重复确认增加版本 | 检查完整性和端点；已确认的有效路线重复确认不写入、不增加版本 |

## 黄包车管理

当前前端没有黄包车页面、代理或菜单，后端已有 `RickshawController` 和 `RickshawService`。现已补齐管理员菜单“黄包车管理”，访问路径为 `/path-seeker/admin/console/rickshaws`。

- 按车号或车夫姓名、目的地、状态查询与分页。
- 通过弹窗新增或编辑车号、车夫、备注；编辑时保留归属目的地。
- 状态包括启用、停用、维修、退役，退役需要确认。
- 获取、显示和下载二维码；普通获取使用 `rotate=false`，更换二维码需确认旧码失效。
- 查询按北京时间计算的日期范围绩效，默认显示今日数据。
- 主键始终作为字符串透传；请求失败释放操作锁；旧查询响应不覆盖新筛选结果。

车辆归属目的地必须是后端允许的启用户外类型。目的地下拉支持远端关键词搜索。二维码目标地址使用后端配置，前端不推测游客端地址。

## 验证与范围

前端测试覆盖 29 个场景，包括重复保存、实际并发、部分失败重试、跨段撤销、站点移动、坐标转换、加载失败、换路线的晚响应、黄包车重复创建锁及二维码获取不轮换，以及单段生成与整线就绪的区别、自动路段的端点校验提示。

```sh
node --test --test-isolation=none apps/web-admin/tests/*.test.mjs
pnpm --filter @path-seeker/web-admin typecheck
```

后端针对路线保存、生成、几何及黄包车服务的 59 项回归测试全部通过。前端 29 项测试和 Nuxt 类型检查通过。站点重排测试模拟活动编号唯一约束；并发测试通过暂停规划请求使两个服务实例实际重叠执行。新增用例验证旧整线状态不会误挡有效路段、单段生成后准确报告剩余失败段，以及自动生成的端点仍需满足连接校验。

```sh
dotnet test CulturalTourismSystem.ApiTests/CulturalTourismSystem.ApiTests.csproj --no-restore --filter "FullyQualifiedName~RouteMapSaveTests|FullyQualifiedName~RouteMapGenerationTests|FullyQualifiedName~RouteLineGeometryTests|FullyQualifiedName~RickshawServiceTests" -p:NuGetAudit=false --verbosity quiet
```

另外对“后海黄包车长线 A+B”进行了只读数据库检查：截图显示版本 86，检查时数据库已经是版本 88，含 28 个站点及 27 个有效自动路段，且已确认。各段编号、站点对、坐标系和端点连接均有效。将该快照交给当前 RouteMapService 的读取和校验方法，结果为 ready、零条校验问题、版本仍为 88；检查过程中没有写数据库或调用路径规划。当前数据不能还原截图版本 86 时的具体失败段。

上述验证包括本地状态层、服务回归和真实路线的只读快照校验，没有进行真实数据库写入、地图供应商和游客扫码的端到端联调。后端路线锁作用于同一进程的 RouteMapService 请求；跨进程部署或其它服务直接写站点仍需数据库事务及并发控制验证。重排包含多次仓储写入，数据库异常或进程中断的原子性仍需真实数据库验证。

已膨胀的历史折线不会自动清理。可单段重新自动生成后校核，或删除多余顶点再保存；覆盖人工路段会明确提示确认。前后端需要同时更新后，线上才会使用这些修复。
