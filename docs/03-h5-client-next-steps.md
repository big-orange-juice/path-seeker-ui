# H5 Client 下一步迁移计划

本文档用于承接 `apps/h5-client` 当前阶段的后续工作，聚焦真实可玩的 C 端 H5 任务流程，而不是继续扩散式补页面或保留历史兼容包袱。

## 1. 当前结论

| 项目 | 结论 |
| --- | --- |
| 当前主端 | `apps/h5-client` 作为新的 C 端 H5 主实现 |
| 当前架构方向 | 基于 `Vue 3 + Vite + Pinia + Tailwind + shadcn-vue` 的纯 Web H5 方案 |
| 当前玩法收敛 | 仅保留 `普通选择题` 与 `拼图` 两种 renderer |
| 当前流程重点 | 围绕真实任务路线完成“列表 -> 详情 -> 章节 -> 识别/播片 -> 作答 -> 下一章节”主链路 |
| 不再继续投入 | 地图相关业务、本轮无关的 7 种 renderer、mock 数据残留 |

## 2. 下一阶段目标

| 目标 | 说明 | 完成标志 |
| --- | --- | --- |
| 打通主链路 | 让用户可以完整走完一条任务路线 | 核心页面无断链，关键节点都能进入下一步 |
| 完成真接口收口 | 页面只显示后端真实返回字段，不补写描述型内容 | 页面文案、卡片信息、章节信息均来自接口 |
| 稳定关键交互 | 拍照/识别、播片、答题、章节跳转形成稳定 H5 体验 | 异常态与成功态都有明确反馈 |
| 收紧状态模型 | 避免流程状态分散在页面中 | 关键业务状态统一进入 store 体系 |
| 为第二阶段共享做准备 | H5 稳定后再反推 web-admin 的共享 UI 与样式收敛 | 可识别出可沉淀到 `packages` 的基础层 |

## 3. 执行优先级

| 优先级 | 模块 | 核心任务 | 预期产出 |
| --- | --- | --- | --- |
| P0 | 任务主流程联调 | 逐页核查任务列表、任务详情、章节选择、识别、播片、答题、下一章节 | 一条真实任务可以完整游玩 |
| P0 | 真接口清查 | 移除任务卡片、详情、章节、答题结果中的 mock 字段、假描述、补充文案 | 页面仅消费真实接口返回 |
| P0 | 识别流程稳定化 | 处理上传、扫码、权限拒绝、识别失败、重试等分支 | 线下馆内核心玩法可用 |
| P1 | 播片与章节衔接 | 以 `assets/movie` 作为测试素材，打通识别成功后播片，再进入答题 | 播片与章节节奏完整 |
| P1 | 状态管理统一 | 收拢 mission / auth / task / player 等状态，减少页面直接维护流程状态 | 双端可复用的共享状态模型雏形 |
| P1 | Toast 反馈体系 | 统一成功、失败、加载、无权限、提交中、网络异常反馈 | 移动端交互反馈一致 |
| P1 | Renderer 清理 | 继续移除另外 7 种 renderer 的遗留类型、组件和分支 | 渲染层只保留当前业务需要的两种题型 |
| P2 | 容器与布局一致性 | 统一首页与其他页面的移动端壳、留白、安全区、滚动区表现 | 全部页面保持一致的移动端视觉边界 |
| P2 | 共享 UI 收口 | 将已稳定的基础元素继续沉到 `packages/ui` | 为后续 web-admin 接入共享层做准备 |

## 4. 推荐执行顺序

| 顺序 | 工作项 | 原因 |
| --- | --- | --- |
| 1 | 任务主流程联调 | 这是当前是否“可用”的首要判断标准 |
| 2 | 清除 mock 与补写描述 | 避免联调建立在假数据和假文案之上 |
| 3 | 识别流程与播片衔接 | 这是最接近真实线下用户体验的关键环节 |
| 4 | 统一 store 与 toast | 把跑通后的流程沉淀成可维护架构 |
| 5 | 清理 renderer 残余 | 与当前产品方向保持一致，减轻历史负担 |
| 6 | 推进共享 UI | 为 H5 稳定后的双端统一打底 |

## 5. 分阶段任务拆解

### 5.1 第一阶段：主链路可玩

| 任务 | 内容 | 验收标准 |
| --- | --- | --- |
| 任务列表联调 | 核查任务列表字段、卡片展示、进入详情 | 能正常展示并进入详情页 |
| 任务详情联调 | 核查详情信息、开始入口、恢复入口 | 能开始任务或恢复任务 |
| 章节选择联调 | 核查章节列表、章节状态、自由选择逻辑 | 可自由进入任意章节 |
| 识别环节联调 | 接通拍照/上传/扫码后的识别流程 | 失败可重试，成功可进入播片或答题 |
| 播片后答题 | 识别成功后进入播片，播片结束进入当前题目 | 节奏无断档 |
| 下一章节跳转 | 完成答题后默认进入下一章节，同时保留返回章节选择入口 | 主流程连续可走 |

### 5.2 第二阶段：数据与状态收口

| 任务 | 内容 | 验收标准 |
| --- | --- | --- |
| 去除 mock 残留 | 清掉描述性兜底、演示字段、模拟章节数据 | 页面只读真实接口 |
| 统一任务状态 | 明确当前任务、当前章节、作答状态、播放状态、识别状态存放位置 | 页面不再重复维护流程状态 |
| Token 与鉴权复核 | 确保所有真实接口请求都稳定带上 bearer token | 无鉴权遗漏 |
| 错误态统一 | 网络异常、接口异常、识别失败统一走反馈体系 | 用户可以理解当前状态 |

### 5.3 第三阶段：结构收尾

| 任务 | 内容 | 验收标准 |
| --- | --- | --- |
| Renderer 收缩 | 移除无用 renderer 分支与注册逻辑 | 代码结构收敛到两种题型 |
| 移动端壳统一 | 修正页面容器、边距、安全区、滚动体验 | 所有页面视觉壳一致 |
| 共享 UI 继续沉淀 | 收拢 button、input、card、feedback 等基础层 | H5 端基础 UI 更稳定 |
| web-admin 第二阶段准备 | 盘点后台中可复用的组件和样式 | 为后续双端统一制定清单 |

## 6. 当前明确不做

| 项目 | 处理策略 |
| --- | --- |
| 地图相关业务 | 本轮直接放弃，不纳入当前迁移范围 |
| 其余 7 种 renderer | 不再继续维护，只保留清理和移除工作 |
| mock 数据体系 | 不再新增，不再保留，不再依赖 |
| 小程序兼容写法 | `h5-client` 只面向 H5 手机浏览器，不做 uni-app 多端兼容妥协 |

## 7. 完成标准

| 维度 | 标准 |
| --- | --- |
| 流程 | 用户可以从任务列表进入并完成一条任务路线的关键节点体验 |
| 数据 | 页面展示完全基于真实接口返回 |
| 交互 | 识别、播片、答题、切章、错误反馈都有稳定结果 |
| 架构 | 关键业务状态进入统一 store，renderer 收敛为两类 |
| 后续扩展 | H5 稳定后可以顺势进入共享 UI 与 web-admin 收口阶段 |

## 8. 一句话判断标准

如果当前版本已经能够让真实用户在手机浏览器里顺畅完成“选任务、进章节、识别、看播片、答题、继续下一章节”的完整体验，并且页面只依赖真实接口数据，那么这一阶段就算真正完成。
