# 景点 MP3 播放压测总结

整理日期：2026-11-14。时间采用北京时间，流量 GB 采用十进制，内存 MiB/GiB 采用二进制。

## 1. 结论与适用范围

**在本次配置和测试场景下，40 个车夫房间、80 位独立游客可以完成整条路线，18 个景点对应的既有 MP3 均正确进入播放链路并完成。服务端资源有余量，但本次没有测出系统最大承载人数。**

本报告以最终批次 `load40x80-20261114-r6-mp3` 为准：每隔 10 秒出发一辆车，每车 2 位游客，全程不模拟车夫讲话。既有景点 MP3 的播放不需要本轮实时调用 MiniMax 合成。之前包含讲话的测试曾遇到 MiniMax 限流，应与本轮景点 MP3 结论分开。

**手机退后台、锁屏后持续出声仍存在技术风险，尚不能判定真机验收通过。** 本轮运行的是控制台客户端，证明了服务端触发、供流、接收音频内容和业务完成状态；没有实际驱动支付宝手机端扬声器。相关技术风险及验收矩阵见[支付宝技术栈与后台播放风险](./alipay-technology-stack-and-background-audio-risk-20261114.md)。

测试完整经过登录与权限检查、创建房间、游客加入、创建游览及音频会话、模拟沿路定位、逐站触发、接收音频、完成游览和关闭房间。

| 检查项 | 结果 |
| --- | --- |
| 完成游客 | 80 / 80，数据库游览状态为完成 |
| 景点完成记录 | 1440 / 1440，即 80 人 × 18 站 |
| 接收的完整 MP3 | 80 / 80 完整解码成功，0 解码警告 |
| 对应内容验证 | 1520 / 1520 个片段匹配，即 80 人 × 19 段音频 |
| 内容匹配质量 | 最低归一化相关系数 0.94679，通过阈值 0.85 |
| 模拟讲话 | 上传数和讲话输入事件均为 0 |
| 最终复核 | 40 车全部通过，共 800 项检查通过、0 项失败 |
| 收尾 | 40 房间全部关闭，0 取消，0 清理失败 |

内容验证对每段取约 3 秒 PCM，与线路配置指向的原始 MP3 做波形互相关；另外执行全文件解码和数据库核对。它证明每段取样匹配，不等于逐秒人工听审。控制台播放确认也不能替代手机原生播放器的实际播放时钟。

### 原始断言误报说明

原始测试新增的章节检查只收集主讲解，漏算了 `extraAudios` 中合法的“钟鼓楼鼓乐”。因此原始每车结果为 18 项通过、2 项失败，40 个进程均非零退出；但所有车辆都完整跑完，没有发生全局取消。

修正预期收集逻辑后，使用当次保存的线路快照、最终播放时间线和原始结果离线重新核验，得到 **800 / 800 项通过**，并用实际接收 MP3 和数据库记录交叉验证。原始失败记录、退出码和文件证据均保留；不能将此报告理解为原始脚本一开始就全部通过。

### 到站触发与排队

到站后按业务规则排队，上一段讲解未结束时，下一站不会立即打断它。本轮最长到站排队约 **92.813 秒**，期间播放前序内容；音频被调度选中到服务端开始播放，最大约 **0.211 秒**。

因此，正确触发代表“按路线进入队列并播放对应音频”，不代表“到站瞬间就从手机扬声器开始播放”。业务排队、服务端调度、网络接收以及手机播放器缓冲应分别分析。

## 5. 流量计算

96 kbps 为每位游客音频流的码率。纯音频估算公式为：

`流量（GB）= 码率（kbps）× 1000 ÷ 8 × 游客数 × 秒数 ÷ 1,000,000,000`

| 口径 | 流量或速率 |
| --- | ---: |
| 1 位游客听 20 分钟，纯音频理论值 | 14.4 MB |
| 80 位游客各听 20 分钟，纯音频理论值 | 1.152 GB |
| 80 路持续播放，纯音频理论速率 | 7.68 Mbps |
| 80 路持续播放 1 小时，纯音频理论值 | 3.456 GB |
| 本轮实际收到的 MP3，包含末段收尾 | 1,206,003,642 字节，约 1.206 GB |
| 后端网卡实际总出站 | 2,403,604,724 字节，约 2.404 GB |
| 后端网卡实际总入站 | 760,331,252 字节，约 0.760 GB |

网卡统计窗口为 20:23:22.685–20:51:35.502，包含状态查询、确认、其他接口、协议及服务器其他流量。它不是专属 MP3 流量，也不是云账单精确值。入口代理流量未单独采样；如果代理与后端之间走公网，两端是否分别计费要按云账单核对，不能简单把统计值乘二。金额需要再乘以实际出网单价。

原入口代理只有 3 Mbps，会限制整个链路；后端带宽充足不能绕过入口瓶颈。两台提高带宽后本轮完成，但本报告不把之前所有超时都归因于带宽。

## 6. 容量判断与后台播放风险

可以确认的是：**本轮验证到 40 房间 / 80 游客，在既定路线、96 kbps、热缓存条件下运行有资源余量。** 不应根据 CPU 占用或 100 Mbps 带宽按比例推算一个已保证的用户上限。源码中的 `TourAudio:MaxSessions=128` 是会话配置上限，不是“128 人已经压测通过”。

本轮未覆盖多路线、多语言、冷缓存、高于 80 游客、持续数小时运行、全部代理资源、真机后台及弱网故障注入。下一阶段容量验证应分档提升并同时监控入口代理和后端；后台功能验收则应独立使用支付宝真机。

后台播放的核心风险包括：支付宝和操作系统对长连接音频的行为差异、后台 JavaScript 挂起后的断流恢复、原生播放器缓冲、电话和耳机等音频焦点中断，以及 API 重启导致进程内会话丢失。服务端持续供流可以降低依赖游客端 JavaScript 切换景点的风险，但不构成所有手机锁屏持续出声的保证。

上线验收应分开签结论：**服务端本场景通过；支付宝真机锁屏连续播放及异常恢复待验收。**
