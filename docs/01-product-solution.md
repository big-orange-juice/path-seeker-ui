# 博物馆导览解密项目产品方案（简化版）

## 1. 产品定义

| 维度 | 说明 |
| --- | --- |
| 项目名称 | Path Seeker Museum / 秘径寻踪 |
| 产品目标 | 把传统看展升级为“边探索、边解谜、边获得故事反馈”的导览体验 |
| 产品形态 | B 端管理后台 + C 端微信小程序 |
| B 端用户 | 博物馆管理者、策展人、教研人员、活动运营人员 |
| C 端用户 | 亲子家庭、学生、年轻游客、普通散客 |
| 核心价值 | 提高参与度、停留时长、馆藏内容复用率和活动运营效率 |

## 2. 核心场景

### 2.1 B 端在做什么

| 环节 | 目标 |
| --- | --- |
| 馆藏整理 | 把展品、故事、图片、音频、线索整理成可复用内容资产 |
| 谜题配置 | 围绕馆藏快速生成可玩的题目版本 |
| 路线编排 | 把多个谜题组合成一条有节奏的主题任务 |
| 发布复盘 | 发布活动并根据完成率、提示率、卡点持续优化 |

### 2.2 C 端在体验什么

| 阶段 | 用户感受 |
| --- | --- |
| 接任务 | 进入一个明确主题，而不是看一堆展品介绍 |
| 找线索 | 在展厅中观察、比对、寻找关键细节 |
| 解谜题 | 通过互动逐步推进章节，不是一次性答完整套题 |
| 得反馈 | 获得线索、奖励、结局和知识回收 |

## 3. 产品原则

| 原则 | 说明 |
| --- | --- |
| 内容资产化 | 馆藏、题目、故事、路线都应能复用，不做一次性活动页 |
| 路线游戏化 | 参观路径不只是导航，而是任务推进路径 |
| 低打扰体验 | 手机界面服务于看展本身，不喧宾夺主 |
| 规则要少 | 运营配置应尽量少维度，避免出题和审核过重 |

## 4. 功能范围

### 4.1 B 端功能

| 模块 | 说明 |
| --- | --- |
| 基础内容管理 | 博物馆、展厅、展柜、馆藏、标签、媒体资源 |
| 谜题工坊 | 题型模板、题目配置、提示配置、版本管理 |
| 主题路线 | 剧情开场、章节顺序、解锁条件、奖励配置 |
| 发布审核 | 草稿、审核、发布、下线、版本记录 |
| 运营活动 | 节日主题、限时活动、馆校合作专场 |
| 数据复盘 | 完成率、提示率、卡关题、热门馆藏、复访率 |

### 4.2 C 端功能

| 模块 | 说明 |
| --- | --- |
| 任务大厅 | 主题任务列表、推荐路线、活动入口 |
| 剧情开场 | 开场背景、任务目标、角色引导 |
| 章节地图 | 当前进度、已解锁线索、下一目标 |
| 谜题互动 | 观察、选择、排序、配对、密码、推理 |
| 线索与奖励 | 线索卡、碎片、徽章、称号、图鉴 |
| 结局分享 | 真相揭示、成绩卡、分享海报 |

## 5. C 端体验流程

这一节描述“用户从进入小程序到完成一条路线”的完整体验。目标不是把小程序做成连续刷题，而是把它做成“带章节推进的实地探秘流程”。

### 5.1 使用前提

| 条件 | 说明 |
| --- | --- |
| 使用场景 | 用户已到馆，或准备按馆内路线开始体验 |
| 时长预期 | 单条路线控制在 20-30 分钟 |
| 操作原则 | 每次看手机时间要短，主要注意力仍应回到展品和空间 |
| 引导方式 | 默认由任务目标和章节地图驱动，不依赖复杂教程 |

### 5.2 主流程总览

| 阶段 | 页面/节点 | 用户目标 | 系统输出 |
| --- | --- | --- | --- |
| 1 | 首页 / 任务大厅 | 找到适合自己的任务 | 推荐路线、年龄档、时长、难度、活动信息 |
| 2 | 任务详情 | 判断要不要开始 | 剧情背景、适龄说明、路线长度、奖励说明 |
| 3 | 开场剧情 | 进入任务状态 | 角色引导、任务目标、第一站提示 |
| 4 | 章节地图 | 知道当前该去哪里 | 当前章节、目标展厅、已获得线索、下一步操作 |
| 5 | 展品观察 / 线索页 | 先看展品，再理解问题 | 展品说明、观察点、故事片段、可交互入口 |
| 6 | 谜题页 | 完成一次有效解谜 | 题目反馈、是否过关、提示入口 |
| 7 | 章节过场 | 感受到推进与收获 | 新线索、剧情推进、奖励碎片、下一目标 |
| 8 | 终局结算 | 获得完整闭环 | 真相揭示、成绩卡、奖励、分享页 |

### 5.3 详细体验步骤

#### Step 1：进入首页 / 任务大厅

| 项目 | 说明 |
| --- | --- |
| 页面目标 | 让用户在 5-10 秒内理解“这里不是展品目录，而是可玩的主题任务入口” |
| 首屏信息 | 今日推荐、热门路线、亲子优先、限时活动 |
| 筛选信息 | 年龄档、路线时长、主题类型 |
| 用户动作 | 浏览路线卡、切换年龄档、查看推荐理由 |
| 设计重点 | 卡片信息不要太多，重点突出“适合谁、要多久、能玩到什么” |

首页不承担复杂说明，核心作用是快速分流到合适的任务。

#### Step 2：进入任务详情

| 项目 | 说明 |
| --- | --- |
| 页面目标 | 帮用户确认“这条路线值不值得开始” |
| 必要信息 | 剧情简介、适龄、预计时长、章节数、奖励、起点位置 |
| 用户动作 | 点击开始、收藏、分享给同行者 |
| 设计重点 | 文案应强调任务目标和体验收益，不写成普通活动介绍页 |

如果用户是亲子同行，这里需要明确显示“是否适合亲子共玩”，但不再单独引出另一套难度体系。

#### Step 3：选择年龄档并开始任务

| 项目 | 说明 |
| --- | --- |
| 页面目标 | 进入正式任务前完成一次轻量确认 |
| 系统行为 | 根据年龄档加载对应版本的文案、提示强度和题目表达 |
| 用户动作 | 确认年龄档、确认开始 |
| 设计重点 | 这里只做一次选择，进入任务后不再频繁打断用户切换配置 |

年龄档的变化只影响理解方式，不应改变整条路线的核心结构。

#### Step 4：开场剧情

| 项目 | 说明 |
| --- | --- |
| 页面目标 | 把用户从“浏览模式”切到“任务模式” |
| 内容结构 | 任务背景、引导角色、当前目标、第一站提示 |
| 时长控制 | 15-30 秒内完成，不做冗长叙事 |
| 用户动作 | 阅读 / 听旁白，进入第一章节 |
| 设计重点 | 开场只交代必要悬念和第一目标，不一次性讲完整个故事 |

开场之后要立即把用户送到第一站，而不是继续堆说明。

#### Step 5：进入章节地图

| 项目 | 说明 |
| --- | --- |
| 页面目标 | 让用户持续知道“我现在在哪、接下来去哪、已经拿到了什么” |
| 核心信息 | 当前章节、已解锁线索、待完成目标、路线进度 |
| 用户动作 | 查看当前位置、进入目标展品、回看线索 |
| 设计重点 | 地图页应是全流程枢纽，不是单纯展示进度条 |

章节地图承担三个职责：

- 给方向：下一步去哪。
- 给反馈：已经完成多少。
- 给记忆：目前掌握了哪些线索。

#### Step 6：到达展品，进入观察与线索页

| 项目 | 说明 |
| --- | --- |
| 页面目标 | 先把用户的注意力拉回展品本身，再进入答题 |
| 页面内容 | 展品图、位置提示、观察点、简短故事、可疑细节 |
| 用户动作 | 对照实物观察、点击查看细节、进入题目 |
| 设计重点 | 先观察后作答，避免一进页面就是题面 |

这里可以包含两层内容：

- 快速观察层：告诉用户该看哪里。
- 线索理解层：告诉用户为什么这个细节重要。

#### Step 7：进入谜题页并完成作答

| 项目 | 说明 |
| --- | --- |
| 页面目标 | 让用户完成一次短时、高反馈的交互 |
| 输入内容 | 观察选择、细节找线索、排序、配对、密码解锁 |
| 用户动作 | 作答、请求提示、重试、必要时跳过 |
| 即时反馈 | 正确反馈、错误反馈、提示反馈、奖励掉落 |
| 设计重点 | 单题停留时间不宜过长，答题要为推进章节服务 |

题目页的反馈规则：

- 答对后立刻给出“线索确认”或“密档解锁”反馈。
- 答错后不强调失败，而是引导重新观察。
- 提示分三级：观察提示、关系提示、直接提示。
- 首期固定渲染器只覆盖 5 类题型：观察选择、细节找线索、排序、配对、密码解锁。`reasoning` 证据推理型题目放到二期。
- 高频题型以 `L1`、`L2` 为主，终局或关键节点先用高难观察选择或密码解锁承接。

#### Step 8：章节过场与推进

| 项目 | 说明 |
| --- | --- |
| 页面目标 | 每完成一题都要让用户感到自己在推进，而不是只清掉一个题目 |
| 页面内容 | 新线索卡、剧情推进、碎片奖励、下一站提示 |
| 用户动作 | 查看新线索、返回地图、继续下一章节 |
| 设计重点 | 过场要短，但必须存在，否则整条路线会缺少节奏感 |

章节过场是 C 端体验里很关键的一环，它负责把“题目结果”转换成“剧情进展”。

#### Step 9：终局题与结局揭示

| 项目 | 说明 |
| --- | --- |
| 页面目标 | 把前面收集的线索汇总为一次明确的高峰体验 |
| 题目定位 | 整条路线只保留 1 个真正的终局题 |
| 用户动作 | 根据前面线索做最终判断或解锁 |
| 系统输出 | 真相揭示、知识总结、称号 / 徽章 / 成绩卡 |
| 设计重点 | 终局要强调“原来前面的观察都有意义”，而不是突然换一套玩法 |

结局页除了奖励，还要完成知识回收，告诉用户这次探秘最终认识了什么。

### 5.4 卡关、暂停与异常场景

#### 卡关处理

| 场景 | 处理方式 |
| --- | --- |
| 用户第一次卡住 | 先给观察提示，鼓励回到实物 |
| 用户第二次卡住 | 给关系提示，帮助连接线索 |
| 用户持续卡住 | 给直接提示，保证可完成 |
| 用户仍不想继续 | 允许跳过，但保留“未完美通关”记录 |

#### 暂停与恢复

| 场景 | 处理方式 |
| --- | --- |
| 中途退出小程序 | 自动保存到当前章节 |
| 用户再次进入 | 直接回到最近章节地图，而不是重新走首页 |
| 用户换设备或弱网 | 至少保证章节进度、已获线索、奖励状态能恢复 |

#### 异常情况

| 场景 | 处理方式 |
| --- | --- |
| 找不到展品 | 给明确位置描述或“附近提示” |
| 网络不稳定 | 优先展示已缓存的当前章节与基础文案 |
| 同行协作 | 允许一个人操作，其他人围绕线索讨论，不强依赖多人设备联动 |

### 5.5 页面关系与信息节奏

| 页面 | 主要职责 | 不该承担的职责 |
| --- | --- | --- |
| 首页 / 任务大厅 | 分流与吸引 | 讲完整规则 |
| 任务详情 | 帮用户决策是否开始 | 承担大量剧情说明 |
| 开场剧情 | 建立任务状态 | 讲完整背景世界观 |
| 章节地图 | 承接全流程导航与进度反馈 | 变成静态路线页 |
| 展品观察页 | 引导看实物和理解线索 | 长时间停留答题 |
| 谜题页 | 完成交互与判断 | 承担复杂剧情推进 |
| 结局页 | 完成奖励与知识回收 | 再开启一堆新任务 |

### 5.6 与当前难度模型的对应关系

| 体验节点 | 年龄档影响 | 难度档影响 |
| --- | --- | --- |
| 任务详情 | 适龄说明、文案表达 | 标注整体挑战程度 |
| 开场剧情 | 旁白长度、表达方式 | 几乎不受影响 |
| 观察页 | 说明直接程度 | 线索显性程度 |
| 谜题页 | 题面长度、概念解释 | 步骤数、干扰度、提示强度 |
| 终局页 | 结果说明深浅 | 最终判断复杂度 |

## 6. 分层与难度模型

过去文档里把年龄、题型、提示次数、步骤数、认知跨度都分散写成了多个维度，编辑和审核时会很重。这里统一收敛成一套简单规则：

- 年龄档只负责“用户能怎么理解”。
- 难度档只负责“题目有多难”。
- 题型模板只负责“用什么方式交互”。

B 端编辑时只需要选择：`年龄档 + 难度档 + 题型模板`。
其余规则由系统默认值带出，不再让编辑人员手动组合过多参数。

### 6.1 年龄档

| 年龄档 | 理解方式 | 文案要求 | 推荐场景 | MVP |
| --- | --- | --- | --- | --- |
| 6-10 | 以观察、简单因果、直接任务为主 | 短句、直接、鼓励感强 | 亲子线、基础教育线 | 是 |
| 10-15 | 能接受关联判断和轻推理 | 有任务感和一点悬念 | 校园线、剧情线 | 是 |
| 15+ | 能接受多线索推理和更高知识密度 | 更克制，允许信息量更高 | 深度路线、成人路线 | 否，后续扩展 |

补充说明：

- `4-6` 不再单独做标准年龄档。
- 如果确实需要覆盖低龄儿童，优先用“亲子陪伴模式”处理，而不是单独再扩一套完整题库规则。

### 6.2 难度档

| 难度档 | 目标体验 | 线索结构 | 作答步骤 | 提示策略 | 适合题型 |
| --- | --- | --- | --- | --- | --- |
| L1 观察型 | 低门槛上手 | 1 个明显线索 | 1 步完成 | 默认给观察提示，可快速重试 | 观察选择、细节寻找 |
| L2 关联型 | 有挑战但不劝退 | 2-3 条线索关联 | 2 步左右 | 保留三级提示 | 排序、配对、简单密码 |
| L3 推理型 | 有明显成就感 | 多线索交叉验证 | 2-4 步 | 默认少提示，必要时可跳过 | 剧情判断、多步推理、复杂密码 |

### 6.3 配置规则

| 项目 | 规则 |
| --- | --- |
| 年龄档 | 决定文案语气、知识解释方式、默认题面长度 |
| 难度档 | 决定线索显性、步骤数、干扰度、提示强度 |
| 题型模板 | 决定交互形式，不再单独承担难度定义 |
| 提示配置 | 默认跟随难度档，只允许少量人工微调 |
| 版本数量 | 同一母题在 MVP 阶段最多维护 2 个版本，避免版本膨胀 |

### 6.4 路线节奏规则

| 路线阶段 | 建议难度 | 目的 |
| --- | --- | --- |
| 开场 1-2 题 | L1 | 让用户快速进入状态 |
| 中段主流程 | L2 | 保持推进感和参与感 |
| 终局题 | L2 强化版或 1 题 L3 | 建立记忆点和完成感 |

### 6.5 不再分散控制的维度

| 旧维度 | 新处理方式 |
| --- | --- |
| 提示次数 | 收敛进难度档默认策略 |
| 选项干扰度 | 收敛进难度档 |
| 步骤数 | 收敛进难度档 |
| 文案长短 | 收敛进年龄档 |
| 题型复杂度 | 由题型模板决定，不再单独作为难度维度 |
| 认知跨度 | 通过“年龄档 + 难度档”共同约束 |

## 7. 首期固定题型库

首期不追求题型数量，而是先固定一组可以稳定复用的渲染器。这样 B 端配置、C 端渲染、后台预览和后续埋点都可以围绕同一套模板工作。

### 7.1 首期固定题型

| templateType | 中文名 | 渲染器 | 推荐难度 | 说明 |
| --- | --- | --- | --- | --- |
| `observe_choice` | 观察选择 | `ObserveChoiceRenderer` | L1-L2 | 单选式观察题，最适合首屏和基础章节 |
| `clue_find` | 细节找线索 | `ClueFindRenderer` | L1-L2 | 在图上或实物观察目标上寻找明确线索 |
| `sort` | 排序 | `SortRenderer` | L2 | 适合工艺顺序、时间顺序、剧情顺序 |
| `match` | 配对 | `MatchRenderer` | L2 | 适合作者、时代、用途、纹样等关系配对 |
| `code_break` | 密码解锁 | `CodeBreakRenderer` | L2-L3 | 适合章节收束和终局高峰题 |

### 7.2 暂不进入首期固定渲染器的题型

| 题型 | 处理方式 | 原因 |
| --- | --- | --- |
| `reasoning` 证据推理 | 二期再做专用渲染器 | 需要更复杂的证据区、推理区和反馈结构，首期容易把交互做散 |
| 长文本输入 | 暂不支持 | 对线下节奏破坏大，完成率风险高 |
| 长语音问答 | 暂不支持 | 成本高，环境噪音对体验影响大 |
| 重拼图类 | 暂不支持 | 游戏感强，但对导览主流程帮助有限 |

### 7.3 题型使用规则

| 规则 | 说明 |
| --- | --- |
| 开场题 | 优先用 `observe_choice` 或 `clue_find` |
| 中段题 | 以 `sort`、`match` 为主 |
| 高峰题 | 优先用 `code_break` |
| 同一路线内 | 尽量不要连续出现 3 题相同题型 |
| 首期终局 | 不强上 `reasoning`，先用高难 `code_break` 或组合线索题承接 |

## 8. 主题路线设计规则

| 项目 | 建议 |
| --- | --- |
| 单条路线时长 | 20-30 分钟 |
| 节点数量 | 8-12 个关键节点 |
| 章节数量 | 3-5 个章节 |
| 高峰题数量 | 每条路线只保留 1 个真正的高峰题 |
| 奖励结构 | 完成奖励 + 隐藏线索奖励，两层足够 |
| 亲子模式 | 不单独重做题库，优先增加陪伴提示和协作任务 |

## 9. MVP 建议

| 类别 | 范围 |
| --- | --- |
| 馆数 | 1 个馆 |
| 主题路线 | 1-2 条 |
| 年龄档 | 先支持 `6-10` 和 `10-15` |
| 难度档 | 以 `L1`、`L2` 为主，少量 `L3` 终局题 |
| 题型 | 观察选择、细节找线索、排序、配对、密码解锁 |
| B 端 | 馆藏管理、谜题工坊、主题编排、发布审核、基础数据看板 |
| C 端 | 任务列表、剧情开场、章节地图、题目互动、奖励页、结局页 |

## 10. 核心指标

| 维度 | 指标 |
| --- | --- |
| 参与度 | 启动人数、开始率、平均会话时长 |
| 完成度 | 通关率、章节流失率、终局到达率 |
| 难度表现 | 平均提示次数、卡关题 Top10、跳过率 |
| 传播与复访 | 分享率、复访率、勋章领取率 |

## 11. 结论

| 项目 | 结论 |
| --- | --- |
| 产品本质 | 内容运营平台 + 线下实景轻游戏 |
| B 端重点 | 降低内容配置成本，减少出题规则维度 |
| C 端重点 | 强调探索、线索、章节推进，而不是做成普通答题工具 |
| 难度策略 | 只保留“年龄档 + 难度档”两层控制，题型只做交互承载 |
| 落地策略 | 先做少量路线、少量题型、少量版本，把节奏和完成率跑通 |
