# 40 车夫 / 80 游客压测报告

测试日期：2026-11-14，时区：Asia/Shanghai。最终批次：`load40x80-20261114-r4`。

## 结论

100 Mbps 扩容后，实际建立了 **40 个独立车夫房间、80 个独立游客媒体连接**，每 10 秒发一车，80 路同时在线持续 **866.341 秒（14 分 26 秒）**。满载服务器 CPU 平均 **17.78%**、峰值 **19.78%**，API RSS 平均 **498.78 MiB**、峰值 **595.32 MiB**。该场景下后端 CPU、内存有明显余量。

**本轮完整业务验收未全部通过：26 辆通过，1 辆语音插播失败，13 辆被编排器取消。不能将 14 个非零退出进程都归类为业务故障，也不能宣称 40 辆全程全部通过。**

失败车辆为第 27 辆：两个游客均完成 18 站到达和 18 站讲解，路线音频连续且可解码，但车夫讲话没有产生可播放音频。服务器同一请求跟踪记录确认 MiniMax TTS 连续限流，经过 2、4、8 秒退避重试后失败，5 段合成都记录 `AudioChunks=0`。这是本轮已定位的业务依赖故障。

39 个账号为 `loadtest_20261114_driver_01` 至 `loadtest_20261114_driver_39`，均通过正常登录和 `canHost=true` 验证。账号清单位于 `outputs/tour-audio-optimization/loadtest-driver-accounts.json`；随机密码保存在 Windows 当前用户 DPAPI 加密文件 `loadtest-driver-accounts.dpapi`，报告不包含密码或 token。

## 满载资源

CPU 按整台 8 逻辑 CPU 服务器归一化；API CPU 也是整机口径。RSS 是 API 进程驻留内存，不等于整机所有服务的占用。

| 满载指标 | 平均 | P95 | 峰值 |
| --- | ---: | ---: | ---: |
| 整机 CPU | 17.78% | 18.66% | 19.78% |
| API CPU / 整机容量 | 16.66% | — | 18.77% |
| API RSS | 498.78 MiB | 521.84 MiB | 595.32 MiB |
| 后端 eth0 出站速率 | 15.68 Mbps | 16.96 Mbps | 17.88 Mbps |

- 全程最低 MemAvailable：9684.10 MiB，约 **9.46 GiB**。
- API 线程数峰值：39；API PID 保持 `1663367`，未因本轮重启。
- 首次监控基线 API RSS 约 435 MiB；末次采样约 549.52 MiB，CPU 约 0.37%。连接释放后 CPU 已恢复空闲，RSS 未立即回到基线；本轮不足以证明长期无泄漏，也不能据此认定泄漏。
- 331 个约 5 秒采样点中，303 个点发现原生 LAME 映射；结束后映射卸载。
- FFmpeg 大部分采样为 0，仅 2 个采样点各出现 1 个进程，未出现随 80 位游客增长的常驻 FFmpeg 群。未保存该短时进程的完整命令行，因此不将其用途写成确定结论。
- 日志中原生编码回退、共享解码回退、会话创建超时、会话创建失败、路线音频解码失败均为 0。

结论适用于本次 40 房间 / 80 游客场景，不能按 CPU 占用率直接线性推算支持数百或上千用户。第三方 TTS 配额、路线/语言差异、冷启动、缓存占用及带宽都可能先成为限制。

网卡计数采样窗口为 **19:43:49.284–20:11:22.039**，包含启动前及停止后的少量空闲采样：

- eth0 统计包含整台后端服务器的其他流量、SSH 监控、协议开销、音频、状态查询/确认等，并非云账单的精准计费值，也不是仅音频流量。
- 本地接收 MP3 的 1.185 GB 是音频有效载荷，部分车辆最后一段因全局停止被截短，不能当成 40 车完整结束的固定流量。
- 只接入了后端 SSH，**未采集入口代理服务器的 CPU、内存及网卡计数**；两台机器的实际计费总量需要云监控或账单核对。若后端到代理走公网，可能存在两段出站计费；若走同 VPC 内网，应按实际计费规则区分，不能简单将一个网卡值乘二当账单。

理论计算（十进制 MB/GB）：

```text
单游客音频：96,000 bit/s ÷ 8 = 12,000 byte/s
80 游客音频峰值：96,000 × 80 = 7.68 Mbps
80 游客各听 20 分钟：12,000 × 80 × 1,200 = 1,152,000,000 byte ≈ 1.152 GB
如每人含收尾播放约 1,256 秒：约 1.206 GB 纯音频
```

错峰出发会改变峰值出现时间，不会减少每位游客听完整行程的音频总字节。本轮状态查询与播放确认返回完整状态，实际总流量显著高于纯音频估算。若全天持续 80 路，仅音频约 3.456 GB/小时；按本轮满载总出站平均速率粗算约 7.06 GB/小时，仅用于相同请求节奏下的预算参考。

流量费用需代入实际单价：`计费出站 GB × 元/GB`。未获得云账单价格，因此不虚构人民币费用。

## 建议及验收边界

1. 维持入口代理和后端足够带宽，避免继续使用 3 Mbps 代理承载这类负载。原 3 Mbps 即使只算音频也仅约 31 路，完整接口开销会进一步降低容量。
2. 优先核对 MiniMax 当前账户的实际 RPM/并发额度和同账户其他任务用量；针对实时 TTS 增加跨房间统一限速、有限队列及可见的失败提示，并验证可用的备选合成路径。单房间指数重试仍可能持续命中共享额度。
3. 补齐 40 车完整业务验收时，应在 TTS 限流问题处理后重跑，保留失败计数，允许无致命错误的其他车辆完成。本轮已经完成容量观测，业务全通过仍未获得。
4. 扩大并发或上线前，另做多语言/多路线、冷缓存和长时间运行测试；本轮每车只有一次 8 秒讲话，不代表 40 个车夫持续讲话的第三方服务负载。
