# 交互优化问题 1：解说中的视频/图片插播可行性

## 结论

可行，但需要把它作为“讲解时间轴事件”接入，不能只在节点结束后播放现有的节点视频。

当前系统已经具备这些基础能力：

- 本地音频队列支持 `interlude-video`，可暂停音频、打开视频、结束/跳过/失败后恢复原音频位置。
- 服务端持续讲解支持 `hold`、`release`、重连和实际播放时间确认。
- 客户端可以根据播放器实际时间计算当前音频片段的播放进度，而不是使用服务端生产进度；整节点包含多个片段时，还需聚合各片段时长。
- 节点已有图片轮播组件，当前是手动切换，没有自动时间轴触发。

## 当前验证结果

我运行了 20 条专项测试，全部通过：

这些测试通过仓库的模拟播放器、视频事件及请求回执验证代码流程，没有在 Android/iPhone 的支付宝真机上实际解码和播放视频。自动 70% 触发代码仅在测试原型中，使用非跟随模式下已有的视频能力；正式跟随模式尚未接入该触发器。不能将“测试通过”解释为已完成整项需求或已获得真机自动播放保证。本次未修改正式播放器业务逻辑。

- 当前正式行为在播放到 70% 时不会自动弹视频。
- 跟随车夫模式会拦截现有手动视频入口。
- 原型逻辑可以按客户端实际播放时间，在 70% 触发一次视频，即使服务端生产时间已经到 95%。
- 前台视频可以暂停讲解，视频结束、跳过或失败后释放讲解并重连恢复。
- 本地播放器支持按章节边界编排为“前 70% 讲解 → 视频 → 后 30% 讲解”。
- 当前页面隐藏时会结束视频并释放讲解，不会保存视频位置后再续播；这是正式接入前需要补的生命周期策略。

测试文件：`outputs/video-interlude-feasibility/probe.test.cjs`。现有视频行为回归覆盖在 `apps/mp-alipay/tests/tour-media.test.cjs`。

## 推荐实现

建议后台给每个讲解章节增加插播事件，例如：

```json
{
  "chapterId": "chapter-01",
  "trigger": { "type": "progress", "value": 70 },
  "media": { "type": "video", "url": "https://.../video.mp4", "durationSeconds": 28 },
  "resume": "same-position"
}
```

客户端流程：

1. 按播放器实际时间计算当前章节进度。
2. 首次跨过 70% 时记录事件 ID，避免轮询或重复回调导致重复插播。
3. 持续讲解模式先向服务端发送 `hold`，携带当前媒体流和实际播放时间。
4. 前台打开视频；视频播放期间暂停定位切站和自动切节点。
5. 视频结束后发送 `release`，服务端重连并从断点继续。
6. 用户跳过或视频失败时同样恢复讲解，但不标记该视频为完成。
7. 页面隐藏、来电、音频焦点变化时保存“讲解断点”和“视频播放秒数”；返回前台后继续视频，或按产品策略直接跳过视频并恢复讲解。

图片可以复用相同事件模型：轮播本身不抢音频焦点，达到触发点后展示轮播，按设定时长自动切换，讲解可持续播放。若要求图片展示期间暂停声音，也沿用视频的 `hold/release` 逻辑。

## 服务端是否需要改动

需要小幅扩展：

- 讲解内容返回插播事件及稳定事件 ID。
- 持续讲解状态返回当前章节和插播事件状态。
- 记录插播事件是否已触发，防止重连后重复播放。
- `hold/release` 继续使用当前协议；不需要把视频文件混入持续音频流。

视频本身建议由客户端前台 `video` 组件播放。支付宝小程序后台/息屏不能保证视频继续播放；若用户切后台，必须保存视频位置并在回到前台时恢复或跳过。

## 验收建议

至少验证：70% 触发一次、69%→70% 只触发一次、重连不重复触发、视频结束续播、跳过续播、失败续播、问答打断、来电/音频抢占、切后台返回、切换节点、最后节点结束和不同视频时长。真机需要覆盖普通 Android、低端 Android、iPhone，以及车夫正在讲话时的优先级。
