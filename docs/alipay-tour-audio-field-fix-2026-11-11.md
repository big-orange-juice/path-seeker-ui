> 本文为上一轮音频稳定性修复记录。后续到站差异修复和当前诊断版本 `tour-audio-arrival-20261111` 见 [锁屏到站与延迟排查](alipay-arrival-latency-audit-2026-11-11.md)；发布时以该后续记录为准。

日期：2026-11-11。适用于 `tour-audio-stability-20261111` 诊断版本。最新要求是 120 分钟，不再采用此前提到的 50 分钟。本轮需要同时发布 WebAPI 和支付宝小程序。

## 现场记录说明了什么

提供的 Android 记录同时出现 `playing=true` 和 `failed=true`。原生失败后的迟到 Play 回调原先可以重新把页面标成播放中，但这不能证明已经出声。现已阻止这种状态；发生错误后，必须看到有效媒体时间继续推进才清除失败，并保留脱敏后的原生错误码、消息和时间。

同一记录中，服务端 `mediaTimeSeconds=165.2`，播放器 `time=142.397`，相差 22.803 秒。原先页面使用服务端正在生成的节点，因而可能显示新节点，耳朵听到的仍是旧节点。现由服务器记录媒体时间线，前端按原生播放时间映射实际播放的节点、标题和进度。这个差值提示存在时间线或缓冲差异，不能单凭它认定网络延迟恰好是 22.803 秒，也不能据此确定无声的全部原因。

## 已实现的行为

- RxJS `Subject + concatMap` 串行处理媒体控制请求；旧会话和旧意图校验继续保留。退出或替换会话时清理排队任务。界面事件冒泡使用支付宝 `catchTap` 阻止，RxJS 不替代组件事件机制。
- 跟随期间底部播放器和内容页显示只读波形。图文、图片预览、节点浏览入口保留；播放、重播、快进退、拖动、切换导游、队列抢播和手动视频不能启动。页面函数入口也校验状态，避免只隐藏按钮而仍可误触。
- 浏览其他节点不切换媒体、不覆盖当前收听内容，也不会因打开内容页锁住服务端到站调度。播放时间线更新时保留用户正在浏览的图文；浏览不同导游的节点后重连仍保留原会话的导游，避免因为浏览而重建会话。
- 关闭“跟随车夫”立即恢复手动控件，可播放刚浏览的节点，无需离开房间。重新开启跟随后恢复自动讲解和只读控件。
- 跟随模式移除“回到现在”按钮，关闭内容页自动返回正在收听的节点，不重排媒体。新建游客会话会根据司机新鲜定位判定到站；不在有效节点范围内时等待下一节点。每位游客有独立队列，中途加入不等于跳到其他游客音频的同一秒，原会话重连也不会自动清空旧队列。
- 前台跟随时对失败、停滞、断线进行最多 3 次自动恢复，设置递增退避；尊重暂停、问答挂起和原生暂停。锁屏 JS 冻结时不能执行这段恢复逻辑。
- 设置后台播放器 `src` 后不再重复调用原生 `play()`。手动选站、预览、重播和跳转后重新连接媒体，清除旧连接积压的内容；重连仍可能重播尚未确认收听完成的节点。
- 后台采用 96 kbps、44.1 kHz、单声道 MP3，减少 FFmpeg 输入探测等待并及时输出；已解码音频共享缓存、同 URL 在途请求复用、下一章节或节点预取。缓存改善重复下载和解码耗时，不会提升原始录音本身的质量。

## 120 分钟配置

已写入后端 `CulturalTourismSystem.WebApi/appsettings.json`：

```json
"TourAudio": {
  "Enabled": true,
  "MaxSessions": 16,
  "MaxMinutes": 120,
  "MediaBaseUrl": "https://www.omahaaigc.com/",
  "FfmpegPath": "/usr/bin/ffmpeg",
  "DecodedCacheMegabytes": 128,
  "DecodedCacheMinutes": 120,
  "IdleAudio": {
    "Enabled": false,
    "Items": []
  }
}
```

会话有效期从创建时起计算，最多 120 分钟，并受房间剩余有效期限制；关闭房间、结束行程或退出也会提前停止。部署时检查 `appsettings.Production.json` 或环境变量是否覆盖这些值，尤其是 `TourAudio__MaxMinutes`。缓存采用容量和过期淘汰；128 MiB 是共享缓存预算，不含各游客正在使用的音频和 FFmpeg 进程。96 kbps 连续收听两小时约 86.4 MB，不含协议开销；当前 `MaxSessions=16`。

## 空闲节目配置

初次实现时素材尚未提供，配置为 `Enabled=false`、`Items=[]`。后续已按用户要求启用陶瓷路线的 5 段真实中文音频，详见 [当前节目配置](alipay-idle-audio-ceramics-2026-11-11.md)。下方保留单项字段示例，便于后续增加节目：

```json
"IdleAudio": {
  "Enabled": true,
  "Items": [
    {
      "Title": "文人趣事 01",
      "Url": "https://www.omahaaigc.com/替换为实际音频路径.mp3",
      "Language": "zh",
      "RouteId": "2116113373455323136"
    }
  ]
}
```

`RouteId` 保持字符串；不指定时适用于匹配语言的路线。节目按配置顺序循环，最多取 32 项。下载地址须能由 WebAPI 访问且满足现有公网 HTTPS 校验。配置在创建媒体会话时读取，更新配置并发布后应退出旧会话再进入。

优先级为：车夫房间语音 → 已触发的路线讲解 → 空闲节目 → 静音。路线到站后暂停空闲节目的读取，讲解完成后从暂停位置继续；节目不写节点完成进度。节目下载失败记录日志，间隔后重试，不阻止路线讲解。

这是服务端音频编排能力，不是已经证实能绕过系统限制的保活方式。手机预先缓存的节目片段不能从服务器撤回，真正听到切换可能晚于服务器切换；仍需记录真机到站至出声的延迟。

## 发布顺序

1. 发布当前 WebAPI，包含 `TourAudioSessionService`、`TourAudioCodec` 与新的 `appsettings.json`；重启服务。无需数据库迁移，FFmpeg 继续用 `/usr/bin/ffmpeg`。
2. 已配置好的 `/path-seeker/api/TourAudioSessions/` 流式代理继续使用：`proxy_buffering off`、`proxy_cache off`、`gzip off`。不要给持续媒体响应配置 CDN 缓存；缓存放在服务器原始素材与解码结果这一层。完整 Nginx 示例见 [部署与验收](alipay-server-tour-audio-deploy-test.md)。
3. 小程序保持 `serverTourAudio: true`，构建产物为 `D:/workspace/amh/code/CulturalTourism/web/path-seeker-ui/apps/mp-alipay/dist`。支付宝开发者工具打开此目录，上传并使用新体验版或发布版。本轮不能只更新其中一端。
4. 游客退出旧房间或旧媒体会话，打开新版本再加入。诊断记录应出现 `tour-audio-stability-20261111`，后端状态应包含 `timeline`；旧会话不会自动变成新编码或新配置。

## 现场验收顺序

Android 和 iPhone 分别执行，使用不同游客账号并记录支付宝版本、系统、机型、网络、会话 ID、到站时间与实际出声时间。

1. 开启跟随，司机进入节点 A：自动出声。打开内容并浏览 B：B 的图文可看，但不能点播，A 的声音继续。
2. 关闭跟随：在内容页播放 B，确认听到 B；暂停、恢复、重播有效。再次开启跟随，恢复波形，不能手动抢播。
3. 开启跟随后在 A 播放中锁屏，断开调试器；A 结束后进入 B，再进入 C，均须不解锁而实际出声。另一台手机录下过程，不用解锁查看状态代替锁屏证据。
4. 节点外等待至少 5 分钟，再进入新节点。素材提供后重复一次空闲节目 → 路线讲解 → 原节目续播，并记录切换延迟。
5. 测试前台断网恢复、问答打断、退出房间后普通播放；检查错误不会显示成正在播放。返回前台后观察有限次恢复，必要时使用“重新连接”。
6. 另安排 120 分钟持续运行，记录到期行为与内存、带宽；本轮只验证了配置和局部媒体用例，没有完成两小时真机耐久测试。

代码和自动化中未保留已复现且未修复的上述问题，但有限测试不能证明不存在任何竞态。服务端日志中的到站或已播送不代表手机已经出声；两种系统的锁屏连续播放必须有实际听到音频的验收证据。
