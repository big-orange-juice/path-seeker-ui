# 路线站点数显示为 0 的修复

## 实际原因

截图中的“后海黄包车长线 A+B”（2110099277161304064）在真实数据库中有 28 个未删除的 route_stage 节点，puzzle_route.puzzle_count 却为 0。后台列表直接展示该汇总字段，前端代理没有改写数值。

BuildOutdoorDraftAsync 创建节点后没有更新路线汇总。普通节点增删使用的 RouteStageService 会重算汇总，但户外草稿直接写仓储，绕过了该步骤。只读检查也发现“后海经典半日线”（610000000000001001）实际有 5 个节点、汇总为 0。

## 修改范围

- 户外草稿创建成功后，将实际创建节点数写入路线汇总。
- 仓储增加按路线 ID 批量统计未删除节点的查询，在数据库中分组计数，不加载节点配置。
- 管理端分页、单行查询和已发布路线卡片按实际节点数量返回既有 puzzleCount 字段。
- 详情与预览使用已加载的节点数量，保证数字和节点列表一致。
- 空路线返回 0，已删除节点不计入；读取不修改真实业务数据。

修改涉及后端仓储接口、仓储实现、PuzzleService 和新增的 RouteStageCountTests。没有修改前端页面、业务校验、节点正文、音频、发布状态或数据库结构。

## 验证

- 站点计数、发布、地图和黄包车定向回归共 72 项通过，0 失败，0 跳过。
- WebApi 构建通过，0 错误；保留原有依赖警告。
- 新增 7 个测试用例，覆盖过时汇总为 0/99、空路线、已删除节点、无绑定开场白、详情与预览、已发布卡片、新草稿写入汇总以及批量读取不写路线。
- 修复后的真实 RouteStageRepository 在强制只读连接上查询：长线 28、半日线 5、不存在路线 0；重复读取结果一致。
- 查询连接设置 default_transaction_read_only=on，没有修补真实数据库汇总值。

这批代码需要由运行中的后端加载后，页面刷新才会显示正确数量。未部署、未重启现有服务，未在浏览器中宣称已验证显示结果。
