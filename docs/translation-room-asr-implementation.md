实施日期：2026-10-27。对应[优化方案](./translation-room-audio-asr-optimization-plan.md)中的 P0/P1 首批，以及识别请求和队列的基础保护。本记录只描述已实现和已验证的内容，不代表整个方案已完成。

2026-10-28 补充的自适应 RMS + WebRTC VAD 实施、配置与限制见第 5 节；前四节保留首批实施记录，其中固定 RMS 为当时的房间默认策略。

## 1. 本批已实现

### H5 采音与 PCM 编码

- `capture.worklet.js` 按实际 AudioContext 采样率聚合约 20ms 音频，通过 transferable 传递独立缓冲；保持默认 800 样本、50ms 的 16kHz 网络包。
- 每包附带连续帧号与起始采样位置，停止确认携带生产帧数和样本数；主线程核对连续性，并提供 `getStats()` 查询消费计数、采样率和最近帧年龄。
- 正常结束先接收 Worklet 尾帧，再排空 PCM 编码器，最后发送 `input.end`。离开、立即关闭、切账号、播放权丢失和异常断线关闭采音门控，丢弃尚未发送的尾帧，不再 flush 编码器。
- 正常停止缺少确认或尾包计数不符时显式报错，不将超时视为已完整收尾。停止期间发生账号切换或退出，会阻止旧尾帧继续上传；旧停止任务完成不会释放新一轮的播放权。
- 保留 AEC、NS、AGC，请求理想单声道和 16kHz；编码始终使用实际 AudioContext 采样率，采集与播放仍使用现有共享上下文。
- 16kHz 输入走直通；其他采样率使用 256 相位、Blackman 窗 sinc FIR 重采样，截止频率 7kHz，滤波半径为 `ceil(48 × inputRate / 16000)`。跨块保留历史，输出位置由累计输出样本数计算，正常排空保留最后输出样本。
- H5 与 demo 接入麦克风 track `ended`、帧号异常、采音回调错误和约 1.5 秒无帧检测。检测到实际中断后停止并提示重新开麦，退出时清理轨道监听器和定时器。

### 回声循环与原文保留修复

用户截图中英文译文再次出现在“中文原声”栏，且确认录音时附近有英文外放。收音、ASR、翻译和译音播放会因此形成反馈循环；语言提示不能代替回声处理。

- H5 房主开麦前登记本机采音状态；同一浏览器配置、同一 origin 下的房间收听页停止当前及排队译音，继续接收字幕和房间事件。新打开的收听页也会读取该状态，播放前再次核对。
- 防回声期间显示对应语言的暂停说明并禁用恢复声音按钮。停麦后从下一个译音段边界恢复，不补播暂停期间的音频。远端游客不受此本地保护影响。
- 采音登记采用独立持有令牌，旧采音的迟到清理不会释放新采音登记；正常停止、异常、退出及页面离开均释放。跨标签页使用 localStorage 与 storage 事件，每两秒续期，15 秒到期兜底处理崩溃页面。页面恢复时重新发布；存储不可用时退回当前页面保护。
- 共享 H5/demo 麦克风保留 `echoCancellation: true`，仅在轨道明确声明支持 `all` 模式时尝试 `applyConstraints({ echoCancellation: { exact: 'all' } })`，失败继续使用原 AEC。`getStats().audioSettings` 提供浏览器实际设置，不把请求的模式等同于已生效。
- H5 与支付宝房主开麦后提示游客使用耳机。不同浏览器、不同配置、不同 origin 和旁边手机的外放无法通过上述本地登记联动；浏览器 AEC 也不保证消除这些声音，现场应使用游客耳机和靠近嘴部的麦克风。
- 共享字幕层按 epoch 和提交序号缓存非空 `transcript.final`，最多保留 120 段。翻译起始事件缺失或迟到时仍能填入原文，空的重复起始事件不再清空原文；退出时清除缓存。该修复同时适用于 H5 与支付宝，不会把已识别到的英文伪造为中文。

能力依据：[浏览器 echoCancellation](https://developer.mozilla.org/en-US/docs/Web/API/MediaTrackConstraints/echoCancellation)、[MiniMax 语音识别](https://platform.minimaxi.com/docs/api-reference/speech-to-text)。MiniMax 的 `language` 是 HTTP header 中的语言提示，当前传法符合文档；本次未修改请求字段或添加未公开参数。

### 服务端切段

后端仓库：`D:/workspace/amh/code/CulturalTourism/git_src/CulturalTourism_System`。

- `PcmSpeechSegmenterOptions` 提供预卷、静音收段、最长段和能量阈值配置，并校验范围与 20ms 帧对齐。
- 翻译房间默认使用 240ms 起音预卷，环形缓冲保留触发前的音频；触发帧只写入一次。
- 保持 600ms 静音收段、4 秒最长段和 RMS 400 的默认参数。通过 `IPcmVoiceActivityDetector` 接口允许后续替换检测器，本批仍使用固定 RMS 检测，尚不能可靠区分风声与人声。
- 每段带独立源序号、绝对采样起止、首次/最后有效语音位置、有效语音样本数，以及 `silence` / `max_duration` / `flush` 原因；样本位置在同一输入 epoch 内累计。
- 正常 `Flush()` 保留短词和强切后的短尾，排空后不重放旧预卷。立即关闭房间时不再额外排空尚未成段的音频。
- 无参数构造仍采用旧切段默认值，私人问答和 `DuplexTranslationSession` 不自动启用房间预卷。

### 识别请求与队列

- 每个房间输入 epoch 冻结一份切段和请求配置，日志版本为 `pcm-preroll-v1`。
- 每段 ASR 默认 30 秒独立超时；单段超时沿用有序 gap 进入提交器，结清并断开缺口两侧的待提交内容，后续段继续识别。
- 保留每房间串行识别和 30 段队列，同时增加默认 120 秒待识别音频的硬上限。该时长只统计尚未开始识别的 PCM，不等于端到端延迟。
- 达到任一队列上限时停止当前输入，记录未接收源段的序号与样本范围，排空已经接收的工作并明确通知输入中断。捕获流程异常不再提前关闭识别结果队列，也不再排空被拒绝段之后的尾音；识别或提交流程异常则取消整个输入处理流水线，避免另一阶段永久阻塞。
- 通过现有 `segment.error` 事件的 `asr_capacity_exceeded` 错误码通知客户端。H5 立即停麦并保留事件连接，支付宝停止录音并关闭房主连接，均禁止迟到尾音继续上传；游客连接继续接收已接受内容的翻译输出。应先部署能够处理此错误码的客户端，再启用更紧的队列限制。
- 每段使用单调时钟记录排队等待、ASR 耗时、RTF、剩余队列秒数、切段信息与结果状态。ASR 耗时不包含向提交队列写入时的背压等待；日志不新增音频内容或识别正文。

## 5. 2026-10-28：自适应 RMS + WebRTC VAD

### 范围与处理方式

讲解房间默认启用 `rms_webrtc`，由服务端统一处理 H5 和支付宝上传的 16kHz、单声道、16 位小端 PCM；不增加外部 API，不改上传协议、翻译及译音播放流程。私人双工翻译仍使用无参数切段器的原 RMS 默认策略。

后端新增 `CulturalTourismSystem.Service/Chat/TranslationRoomVoiceActivity.cs`，依赖 [WebRtcVad.NET 1.0.0](https://github.com/devnull/WebRtcVad.NET/tree/a52dac432a64c2c609addf978c1f766bde6a5264) 的纯 C# WebRTC GMM 实现，无原生 DLL 和神经网络模型。每个输入 epoch 独立创建检测器，输入任务结束后释放；初始化和配置错误显式失败，不静默降级。

- 每个 20ms 帧均经过 WebRTC VAD；RMS 去掉直流分量，辅助拒绝低能量残留和无声音频。
- 噪声底只在 WebRTC 判为非语音且未处于讲话段时更新；限制单帧上升速度及范围，避免突发声或正在讲话抬高门槛。
- RMS 起音阈值为 `clamp(噪声底 × 1.5, MinimumRms, MaxAdaptiveRms)`，段内阈值降低至 `clamp(噪声底 × 1.1, MinimumRms, max(MinimumRms, MaxAdaptiveRms / 2))`。不再用旧的 400 硬门槛挡住所有轻声帧。
- 默认最近 3 帧中至少 2 帧通过才开始一段，当前帧也必须通过；两帧之间允许一次短间断。保留确认前音频和真实采样范围，不把确认等待变成首字丢失。
- 保持默认 240ms 预卷、600ms 连续非语音收段和 4 秒最长段。WebRTC 自身有短暂语音延续判定，实际从讲话结束到收段的时间还受这部分影响。
- 正常停止时，尾部不足 20ms 的音频仅在分类器内部补零，上传给 ASR 的 PCM 和样本范围保持原样。强切后的非零短尾保留；强切后纯静音不产生额外 ASR 段。
- 不按总段长 300ms 一刀切，不按 `Thank you` 或其他文本做黑名单。尚未通过起音确认的单次脉冲会被跳过，因此极短、独立的声音仍存在漏检风险；已确认讲话之后的强切短尾不重新要求两帧起音。
- 未触发讲话段时不调用 ASR，不生成气泡或识别失败提示。已提交的讲话段若遇到 ASR 请求失败、超时或空结果，仍保留原来的错误与 gap 处理。

### 配置与回滚

配置仍位于 `TranslationRoom:Asr`，每次开始输入时读取。默认值写在代码中，不需要覆盖已有 `appsettings.json`。

| 新配置项 | 默认值 | 含义与范围 |
| --- | --- | --- |
| `DetectorMode` | `rms_webrtc` | `rms_webrtc` 为组合检测，`rms` 切回原固定 RMS |
| `WebRtcMode` | 2 | 0～3；越高越倾向过滤，轻声漏检风险也越高 |
| `MinimumRms` | 40 | 有限数，1～400；组合检测的最低 RMS 门槛 |
| `MaxAdaptiveRms` | 200 | 不低于 `MinimumRms`，不超过 1000；组合检测的自适应起音门槛上限 |
| `SpeechStartFrames` | 2 | 1～3；最近 3 帧的起音确认帧数，仅组合模式生效 |

原 `SpeechThreshold=400` 只控制 `rms` 模式；组合模式使用上述两个 RMS 配置。保留原来的其他切段、超时和容量配置。起音确认大于 1 帧时，内部至少保留 40ms 确认窗口，因此 `PreRollMilliseconds=0` 不会吞掉确认前的音频。

需要回滚检测策略时，设置 `TranslationRoom:Asr:DetectorMode=rms`，或者环境变量 `TranslationRoom__Asr__DetectorMode=rms`，在应用配置生效后重新开始输入。回滚不需要调整客户端。

启动日志版本变为 `rms-webrtc-v1`，记录实际检测模式、WebRTC 强度、RMS 门槛和起音确认参数；输入结束日志汇总检测帧数、通过的候选语音帧数和噪声底。候选帧数不代表人工核验的人声时长。日志不记录音频或识别正文。

### 验证与能力边界

- 42 项针对性测试通过，覆盖真实 WebRTC 的静音和尾帧处理、受保护噪声跟踪、低于旧门槛的候选人声、隔离与释放、配置校验、2/3 帧起音、短词、强切短尾以及默认房间输入。原队列容量与超时测试明确选择旧 RMS 模式，继续验证其原本行为。
- 翻译房间、切段、语义提交和双工翻译关联回归共 77 项通过。新增房间集成测试使用真实组合检测与合成音频、模拟 ASR，验证无讲话不请求 ASR，以及合法返回的 `Thank you.` 不被文字过滤。
- WebApi 构建成功，独立验证产物位于后端 `artifacts/rms-webrtc-build`；已有依赖和空引用等警告仍存在。
- 本机 .NET 10 Release / Windows x64 下，纯 C# 分类器与 WebRtcVadSharp 1.3.2 原生实现以 mode 2 对照，4 组合成信号共 8000 帧的判断一致；这不是所有输入、模式和平台的等价证明。
- 微基准对每种信号预热 10000 帧、测量 100000 帧；组合检测约 1.9～2.4 微秒/20ms 帧，测量区间当前线程堆分配为 0。该结果只包含检测调用，不包含实例初始化、切段数组、网络、ASR、日志和房间调度，也不代表生产服务器容量。
- 合成宽带噪声在此次对照中仍被两种 WebRTC 实现判断为语音，因此该组合不能保证过滤所有强噪声；更不能区分房主、路人或外放译音。保留浏览器降噪、防回声和耳机提示。
- 本次没有执行真实供应商识别、户外录音质量评测、移动端收音验收或生产部署。风声、车声、轻声、否定词和外放回声仍需真机验证后调参。
