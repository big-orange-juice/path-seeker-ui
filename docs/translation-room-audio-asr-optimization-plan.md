# 翻译房间收音、ASR 与译音播放优化方案（合并评审版）

更新日期：2026-10-27。

ASR 首批实施进展、实际配置和验证结果见[ASR 优化实施记录](./translation-room-asr-implementation.md)。下文保留方案设计与分批验收要求，各项是否交付以实施记录为准。

本文合并 [原修改清单](./translation-room-audio-asr.md) 与本次收音、识别队列排查建议，并对照源码修正实现风险。本文保留方案与评审结论；已交付的业务修改和自动验证以实施记录为准，供应商能力验证和真机性能测试仍待执行。文中参数和性能目标均为试验起点，不代表已达到的结果。

## 1. 目标、范围与结论

目标是让车夫连续讲解时及时看到识别反馈，让游客以可控延迟听到完整、准确、顺序正确的译音，并避免持续讲解后积压不断增加。

覆盖 H5 与支付宝翻译房间的采音、上传、服务端切段、ASR、语义提交、翻译/TTS 调度和游客播放。私人问答与路线讲解不作为改造对象，但必须验证共享模块的兼容性。

总体判断：原文定位到的固定能量阈值、硬切音频、串行识别积压、语义等待、主线程消息频率和播放积压问题均有依据，适合作为实施线索。需要修正的是：不能把所有建议参数直接作为默认值，也不能用自动丢段、极短文本匹配或无协议的自动重连换取表面的低延迟。

推荐顺序：先观测和修复生命周期，再改采音与切段，再改字幕提交和队列，最后通过真实录音决定是否引入流式 ASR。音频格式变更、同语言并发生成和生产模块迁移单独评估。

### 2.1 已支持多语言输出与同语言共享生成

当前房间支持一条中文输入同时产生英文、西班牙语等多种目标语言的译文和译音。`CommitAsync` 对在线游客订阅语言做 `Distinct()`，每种语言建立一个 `TranslationRoomLanguage` 队列和处理任务；`TranslationRoomState.Send` 按目标语言、成员订阅版本和起始段号分发结果。

例如，5 位游客收听英文、3 位游客收听西班牙语时：

| 环节 | 每个源段或提交段的处理方式 |
| --- | --- |
| 中文 ASR | 每个源音频段执行一次识别，全部目标语言共用结果 |
| 原文语义提交 | 共用一次提交处理，可能合并多个源音频段 |
| 英文翻译/TTS | 每个提交段创建一轮英文生成任务，结果分发给 5 位英语游客 |
| 西班牙语翻译/TTS | 每个提交段创建一轮西班牙语生成任务，结果分发给 3 位西班牙语游客 |
| 网络发送 | 每位游客独立连接、独立有界发送队列；只接收自己订阅语言的音频 |

当前每房间最多同时收听 3 种目标语言，按在线游客实际订阅生成。不同语言可并行处理，但受系统生成并发限制，不保证严格同步起播。相同语言新增游客主要增加分发开销，不应增加已有源段的翻译/TTS 生成任务。新加入游客从服务器确认的后续完整段开始接收。

“同语言只做一轮生成”指共享一轮业务生成及其产物，不要求 TTS 只调用一次 HTTP：当前可按译文片段执行多次合成。暂时性失败重试也可能增加供应商调用次数，不能宣称外部调用具备严格 exactly-once 语义。

### 2.2 LLM Client 的当前生命周期

`ILlmChatClientFactory` 在 `ServiceRegistration.cs` 中注册为单例，但 `LlmChatClientFactory.Create` 每次创建新的 SDK Client；`RealtimeTranslationAgent` 每次判边界和翻译都通过 `using var client = CreateClient()` 创建并释放实例。因此工厂单例不等于 Client 单例。

当前翻译固定使用 DeepSeek 的 `deepseek-flash` 和 `chat/completions` 路径，语言通过请求提示词传入。英文和西班牙语无需仅因目标语言不同而创建不同 Client；可以共享支持并发的底层实例，同时分别发送请求、处理响应。

已安装 SDK 的说明支持客户端并发调用与单例生命周期，但仍需验证项目适配层与请求选项的隔离。Client 对象创建次数、底层连接创建次数、模型调用次数分别统计；仅凭当前每次 new Client，不能断言每次都重新建立 TCP/TLS 连接。

## 3. 对原文建议的取舍

| 原建议 | 评审决定 | 合并后的处理 |
| --- | --- | --- |
| 噪声底跟踪与双门限 | 采纳，作为过渡实现 | 明确 RMS 仍不能可靠区分人声和风声；增加噪声更新保护，并预留真正 VAD 的替换接口 |
| 240ms 预卷、强切保留尾部 | 采纳，分开交付 | 先做无重叠的预卷；重叠必须与采样范围元数据、去重和重复词测试一起交付 |
| 400ms 静音、3 秒最大段 | 作为试验参数 | 与当前 600ms/4 秒做对照，不直接全量替换；短段会增加请求频率并削弱上下文 |
| 最近 300ms 最低 RMS 处强切 | 修正后采纳 | 低能量点不一定是词边界；设置最小有效长度，保留切点之后所有样本，明确无合适停顿时的兜底 |
| 小于 300ms 直接丢弃 | 不直接采纳 | 按有效人声时长、能量和上下文判断；保护“对”“不”“十”等短词及停止时尾音 |
| 标点加停顿直接提交 | 有条件采纳 | ASR 标点不保证语义完整，分语言验证；分号不作为普遍的终止证据，保留从句保护与超时兜底 |
| 等待 3 秒、判边界 600ms | 作为试验参数 | 与完整性、判定超时率共同评估；600ms 若频繁超时，反而可能使内容总等到兜底 |
| CJK 两字、拉丁四字符去重 | 不直接采纳 | 容易删除真实重复词；仅在有音频重叠依据时做受限对齐，并保留跨提交历史 |
| 音频队列 10 段、`DropOldest` | 不作为默认策略 | 按队列音频时长和最老任务年龄治理；默认保护完整性，丢段只能是明确启用且可追踪的降级策略 |
| 429/5xx 固定重试两次 | 修正后采纳 | 请求有总预算，遵守 `Retry-After`，退避加抖动；不重试参数、权限错误，不叠加 SDK 重试 |
| 同语言增加两个生成任务 | 暂缓 | 同语言复用同一个会话，有运行互斥；仅增加信号量不能安全并发，且音频会交错 |
| 客户端缓存即可减少连接 | 采纳复用方向，限定影响面 | 翻译链路使用专用共享 Client 管理器，独立请求和会话；补齐配置轮换、在途请求保护与统一释放，不把对象复用等同于生成结果复用或必然降低模型延迟 |
| 解析供应商 duration 做异常过滤 | 修正后采纳 | 先确认响应字段；PCM 样本数已能计算输入时长。时长/字数只作异常线索，不能直接丢结果 |
| `stream=true` 不是连续实时 ASR | 保留谨慎结论 | 当前只确认使用文件请求；具体接口是否支持文件流式返回或音频持续上行，需查供应商当前协议并验证 |
| 独立 16kHz 采集上下文 | 条件采纳 | 浏览器可能不接受或不实际满足请求；必须读真实采样率并有回退，创建与恢复仍在用户手势内 |
| 二阶 7.2kHz 低通即可抗混叠 | 需要修正 | 截止频率不能代替阻带衰减设计；优先浏览器重采样或经验证的 FIR/polyphase 实现 |
| Worklet 聚合、transferable | 采纳 | 增加尾包排空和消息序号；不能仅凭发送端知道主线程是否丢帧 |
| H5 重连后重发 `input.start` | 不采纳该写法 | H5 `/input` 不发送此命令；重连还要等上一输入轮次结束并确认新 epoch |
| 保持常亮保证锁屏录音 | 修正 | Wake Lock 仅尽力保持屏幕，不能保证后台或锁屏收音；状态中断必须可检测和提示 |
| 每个 buffer 提前 120ms、淡入淡出 | 修正后试验 | 增加提前量会增加延迟；PCM 每块都淡出会造成音量调制，淡化只用于开始、停止或不连续边界 |
| 超过 8 秒直接跳最新 | 不作为默认策略 | 先提示、允许用户恢复到最新；需要以完整段为边界，阻止旧片段迟到后再次入队 |
| 支付宝改传 ArrayBuffer | 暂缓 | 先核对基础库协议和真实二进制收发，不根据浏览器 API 经验替换 |
| 已有停止握手、状态回调、失败清理再实现一遍 | 不重复实现 | 当前已存在 Worklet 停止确认、500ms 兜底、播放器状态回调和开麦失败清理；只补缺失行为 |
| 音频模块移出 demo | 采纳为独立工程任务 | 多入口复用优先抽共享包；保留 Worklet 资源打包和 demo 验证，避免迁移掩盖性能收益 |

## 4. 基础约束与观测设计

### 4.1 必须保持的行为

- 同一源段只识别一次，同语言游客共享翻译与合成；单个游客静音、断线或跳转不能取消其他游客所需的共享生成。
- 已提交的译文和已播放音频不可被迟到草稿、旧连接或重试结果覆盖；草稿不得进入 TTS。
- 缺失音频必须形成明确 gap，清理跨缺口的待提交上下文；不得把前后两句拼成一句。
- 账号切换、退出、正常结束、立即关闭和播放权切换，都能终止相应任务与重连定时器。
- 继续遵守已有独占播放权：房主开麦也参与控制，不能因拆采集上下文而绕过。
- 后端业务主键、`roomId`、`epochId` 和事件标识在客户端与协议中保持字符串；局部序号、时长和采样位置明确范围后可使用数值。

### 4.2 先增加阶段指标

每个音频段记录输入 epoch、局部段序号、采样起止、切段原因、有效人声时长、重叠范围、入队时间、ASR 开始/完成、重试次数、提交等待、翻译首 token、TTS 首包。游客记录完整片段可播时间、实际起播时间、队列剩余秒数、解码失败和非预期断音。

分别统计上行待发送字节、服务端音频队列秒数、最老任务等待时间、各语言待处理年龄和游客可播时长。各队列指标含义不同，不合成一个模糊的“队列深度”。

服务端耗时使用单调时钟；采样位置以本次输入 epoch 为基准。客户端与服务端时钟不可直接相减：跨端延迟通过时钟校准、请求关联或可重复的同步录制测量。首 TTS 包不等于游客已经听见声音。

RTF 定义为识别处理耗时除以输入音频时长，另行记录排队等待；长期处理吞吐低于输入速率时必须处理容量问题。统计 P50/P95，按设备、网络、源语言和目标语言拆分。

默认只记阶段元数据，不输出密钥、音频正文或完整识别文本。真实语料采集单独征得参与者同意并设保存期限。

### 4.3 多语言共享生成的强制约束

- 保留“同房间、同输入 epoch、同一提交段、同一目标语言只调度一轮生成，再向多位游客分发”的现有结构，不得在游客连接或 UI 订阅回调中各自调用模型。
- 原文识别和语义提交在语言分支前完成；英文、西班牙语独立翻译与合成，相同语言的游客共享产物。保留各语言内部的段落顺序。
- 使用房间、epoch、提交段号和目标语言标识生成任务；单独记录任务尝试次数与底层 TTS 子片段，防止重连、重试或多个游客同时加入导致重复调度与重复下发。
- 单个游客静音、慢连接、退出或跳到最新，只处理该游客的分发和播放状态，不取消其他订阅者所需的共享生成。房间关闭才按房间规则取消任务。
- 本次保持同语言统一音色和生成选项。未来若支持每位游客不同音色或语速，应先明确共享粒度与产品约束；不能沿用“同语言一份音频”的成本预期，却按游客重新合成。
- 不强制不同语言等待彼此生成完成；一门语言失败或缓慢，不阻断另一门语言的正常输出。两门语言仍共用系统容量限制，需分别观测队列年龄。

## 5. 第一阶段：采集稳定性与切段质量

### 5.1 H5 采音与编码

1. Worklet 按 20～40ms 聚合，使用 transferable 传递独立音频缓冲；先保持现有 50ms 网络包，对照后再调整。
2. `stop` 时发送未满聚合长度的最后一包，再发送停止确认；正常结束应让最后一包进入编码器、flush 后再发送 `input.end`。当前调用方会先清理活动 socket 标识，新增聚合时必须一起处理尾包门控，避免“收到了确认但最后一包被忽略”。取消时则明确丢弃尾包。
3. 请求理想单声道、采样率与延迟并读取实际结果；设备拒绝指定采样率时回退默认上下文。是否分离采集和播放上下文，结合设备兼容性和资源占用试验。
4. 同为 16kHz 时使用直通路径；其他采样率使用经验证的抗混叠重采样，支持 44.1kHz 等非整数比例，并保留跨块滤波状态。对比波形、频谱、时长和 ASR 结果。
5. 80Hz 高通作为可配置试验项；AEC、NS、AGC 先保留，再用真机比较，避免级联处理损害轻声。噪声跟踪须适应 AGC 带来的幅度变化。
6. 监听 track 结束、上下文挂起、设备变化和页面可见性；回到前台尝试恢复并验证音频帧仍在增长。设备变化先检查实际状态，不无条件抢占或重开麦克风。
7. Wake Lock 作为可选增强，释放时与退出生命周期绑定；申请失败不影响功能，界面只在实际中断时给出准确提示。
8. 用生产帧序号、消费帧序号、音频样本连续性、主线程延迟和上行 `bufferedAmount` 区分堵塞与丢帧。传输队列不得无界增长。

### 5.2 服务端 VAD 与切段

先为切段器注入房间专用配置，保留其他入口默认行为。采用可替换的 VAD 接口：第一版可用自适应噪声底、双门限和持续时间迟滞；后续拿同一批录音比较真正的人声检测模型。

噪声底仅在可信的非人声状态更新，设上下界、突发噪声保护和初始化策略。原稿 `_noise=120`、`2.4/1.3` 等数值作为候选，不能视为适用于所有手机的标定结果。持续背景噪声仍可能骗过能量检测，不能承诺“有城市噪声就绝不请求 ASR”。

候选参数如下；每次试验记录完整配置版本，避免同时调整全部参数而无法归因。

| 参数 | 当前值 | 建议试验范围/规则 |
| --- | --- | --- |
| 判定帧 | 20ms | 先保持 20ms |
| 起音预卷 | 无 | 200～300ms，首轮可用 240ms |
| 连续静音收段 | 600ms | 比较 400/500/600ms，允许按语言与场景配置 |
| 最长音频段 | 4 秒 | 比较 3/4 秒；如缩短，核对请求量和专名错误率 |
| 强切搜索窗口 | 无 | 最近约 300ms，优先可信停顿，不直接等同最低 RMS |
| 强切重叠 | 无 | 先关闭；去重完成后试验 200～300ms |
| 保留尾静音 | 当前随段保留 | 比较约 120～200ms，不提前截掉清辅音或尾字 |
| 极短段处理 | 无统一过滤 | 综合有效人声时长和噪声判断，不按总段长一刀切 |

实现要求：

- 预卷不能重复写入触发帧；强切回退点之后的全部音频必须留给下一段，不得因为回退切点丢样本。
- 区分句尾静音和 VAD 状态退出，避免 400ms 退出后再等待 400ms 才收段。
- 每段带绝对采样范围、有效人声范围、原因及重叠范围；采样位置在同一 epoch 内连续。
- `Flush()` 排空完整采样，正常结束保留短尾；主动取消不额外生成内容。滤波、预卷与重叠状态在新 epoch 重置。
- 噪声短脉冲、真实短词和强切后的短尾分别测试；不能以段长代替是否为噪声的判断。

## 6. 第二阶段：字幕、去重与语义提交

### 6.1 草稿先显示，稳定内容再翻译

分段 ASR 返回后先向房主发识别草稿，明确标注尚未提交；语义确定后继续使用现有 `transcript.final` 与后续翻译事件。分段方案只能做到“每段识别完出现草稿”，不能宣称已经边说边逐字识别。

草稿使用独立源段序号及修订版本，不借用最终讲解段号。它只更新房主当前草稿区域，不追加游客聊天记录，不更新已完成气泡，不进入翻译/TTS。真正流式 ASR 的 interim 未来复用同一约束。

### 6.2 拼接和重叠去重

- 按语言及片段边界处理空白，中文、日文通常不自动插空格；混合语言、拉丁词语跨段和已有空白需单独处理，不能只按源语言做机械拼接。
- 重叠去重仅在音频范围明确相交时启用；优先使用词/字时间戳对齐，没有时间戳时做受限的文本尾首对齐，并评估置信度。
- 同时保留少量已提交尾部和 pending 上下文，否则 pending 清空后下一重叠段仍会重复。历史只用于去重，不修改已提交内容。
- 重叠匹配不确定时保留原文并记录指标，避免删掉“对对对”“北京北京”“不要，不要”等真实重复；不得仅凭 CJK 两字相同就删除。
- 采样范围向后重叠不属于 gap；超出预期覆盖范围的前向缺口才产生 gap。跨 epoch 重置连续性和去重历史。

### 6.3 控制提交等待

将等待时间、最大待提交音频时长和 detector 超时独立配置，分别记录实际命中原因。

- 对可信的完整句末、真实停顿和语言结构做快速判定；以完整性测试决定哪些情况能跳过模型，不能仅凭 ASR 的问号或句号。
- 中文和英文先做试点；日语、韩语、德语等句末结构不完整时保留尾部，标点不充分时交给 detector。
- 将 3 秒提交等待、600～1000ms detector 预算及 6 秒待提交音频时长作为候选，与当前 8 秒/2 秒方案比较。最大等待从第一份待提交识别文本到达开始计算，不等于从用户开口开始的端到端上限。
- detector 支持时设确定性参数和输出上限。`MaxOutputTokens=200` 可能截断较长前缀，需按输入长度和语言给足预算，或者设计可验证的边界位置返回协议。
- detector 超时、输出截断、JSON 无效或前缀不匹配时不改写原文，进入有界兜底；gap 先结清已有内容，再清理跨缺口状态。
- 部分前缀提交后重新核对剩余文本的 deadline、源段范围与音频时长归属，避免把已提交部分的时长继续计入下一次兜底。

## 7. 第三阶段：队列、超时与降级

### 7.1 默认保护完整性，实时降级单独配置

不能只把 30 段改成 10 段。队列同时约束音频秒数、最老等待时间、任务数和内存；强切重叠部分不重复算成新增讲解时长。

建议先在约 3 秒上行待发送音频时提示网络延迟，在服务端最老待识别音频约 5 秒时进入告警；这些是候选告警线，不是触发静默丢弃的默认规则。超过硬上限时停止接收并明确暂停输入、排空已有工作或提示重连，避免终止整个房间和已有游客输出。

若试点明确启用“优先跟上最新”模式，可丢弃尚未识别的完整源段，但必须实现：

1. 可观测的淘汰调度，精确知道丢弃的 epoch、采样范围和原因；仅设 `DropOldest` 不足以完成这项工作。
2. 按序发送 gap，使提交器断开前后语义；已有并发结果不得越过缺口错误拼接。
3. 下发丢段提示并计数；尾部丢弃且随后没有新段，也必须产生通知。
4. 不复用 `TranslationCommit.Reason` 表示没有提交的音频；切段原因、提交原因和丢弃原因分别建模。
5. 同源共享生成保持一致，不让不同游客收到互相矛盾的源段顺序。

### 7.2 ASR 容量与请求策略

先测串行 ASR 的 RTF 和队列趋势。若确有慢请求阻塞，可试验每房间最多 2 路识别，全局另外限流，按源段序号重排后交给提交器。重排窗口必须有界，前序超时转换为 gap，后序结果不得永久等待。

为每段设置房间取消、单次超时和整段总预算。30 秒单次超时可以作为异常保护上限，不能作为实时体验目标；具体预算由真实供应商延迟决定。只对暂时性错误重试，遵守 `Retry-After`，加抖动并在预算耗尽时放弃重试。重试时重新构造请求和文件流，避免流被关闭或读指针在末尾。

当前 429/5xx 信息被包装为普通异常，实施重试前需保留结构化状态和可重试类型；核对 HTTP/SDK 层已有重试，避免相乘放大。失败写 gap，结果按 epoch 与段号去重。

### 7.3 翻译/TTS、权限和持久化

- 先保留同语言串行输出。当前翻译会话存在运行互斥；不能通过新增 `SemaphoreSlim(2)` 并发调用同一个会话。若后续拆翻译和 TTS 流水，要同时设计会话上下文、输出重排、取消、错误传播和全局容量限制。
- 同语言队列也按最老任务年龄治理。只治理 ASR 或本地播放器，无法解决服务端已积压的翻译任务。
- 权限查询只在观测到明显开销后缓存；创建、重连和新开麦强制校验，维护循环保留权限撤销检查。缓存不能绕过用户禁用或车夫授权撤销。
- 若数据库写入成为瓶颈，可改成有界持久化队列；明确重试、幂等键、排空、关闭和进程退出行为。若要求崩溃后不丢记录，应采用持久化任务/outbox，不能用内存 fire-and-forget 宣称可靠保存。

### 7.4 LLM Client 复用的具体方案

目标是减少翻译链路重复创建 SDK Client，并统一管理生命周期；保持第 4.3 节的共享生成结构。Client 复用既不合并英文与西班牙语请求，也不替代同语言结果分发，不以此承诺 ASR 或模型推理速度必然提升。

#### 7.4.1 专用管理器与复用范围

建议新增翻译专用的单例 Client 管理器，例如 `RealtimeTranslationClientProvider`，注入现有 `RealtimeTranslationAgent`，由管理器调用 `ILlmChatClientFactory` 创建实例。

- 相同供应商、模型、规范化服务地址、凭据及影响 Client 行为的超时/重试配置复用一个实例；配置键只存内部，不记录或展示密钥。
- 同一配置下，多个房间、英文/西班牙语翻译及语义边界判定可并发使用该 Client；各自仍有独立请求和取消令牌，并保留现有业务限流。
- 管理器必须防止并发首次访问时重复创建实例；不能用未同步的字段惰性赋值。
- 首版不改变通用工厂 `Create()` 的所有权约定。其他调用方仍可能通过 `using` 释放返回实例，不能把工厂全局改成返回共享实例，导致它们释放翻译正在使用的 Client。
- Client 复用不要求将 `RealtimeTranslationAgent`、房间状态、语言处理任务或会话服务全部改成单例。

#### 7.4.2 请求、会话与取消隔离

| 对象 | 生命周期和隔离方式 |
| --- | --- |
| SDK Client 及底层连接资源 | 按有效配置复用，由专用单例管理器持有 |
| 提示词、源文本、目标语言、`ChatOptions` | 每次调用独立构造，禁止并发修改共享选项 |
| 翻译 Agent 运行对象、流式枚举和响应缓冲 | 每次生成独立，不共享可变运行状态 |
| 房间、语言队列和业务会话 | 保持房间/语言隔离，维持同语言段落顺序 |
| 超时和取消令牌 | 每个判定或生成任务独立；单个游客退出不取消共享任务 |

不能通过共享一个可变“当前语言”“当前消息”字段切换请求，也不能将游客或其他房间的消息历史混入本次翻译。同一 Client 并发调用与同一业务会话并发运行是不同概念；本次不放宽会话互斥。

#### 7.4.3 配置轮换与统一释放

保留配置更新能力：后续调用读取有效配置快照；服务地址、密钥、超时或重试策略变化时创建新实例，供新请求使用。无关配置变化不触发重建。当前固定模型与接口路径的行为不在此次复用改造中顺带改变。

使用租约或等价的在途计数机制保护旧实例：请求从开始到最终响应完成、流式枚举结束或取消清理完毕期间保持租约；配置轮换后旧实例停止接收新请求，最后一个使用者释放后才销毁。不积累永久存活的历史配置缓存，也不因轮换中断在途英文或西班牙语响应。

调用方只释放租约，不再对共享 Client 使用 `using` 或直接 `Dispose()`。管理器由依赖注入容器统一释放；关闭时拒绝新租约，未完成请求通过服务关闭流程取消并清理，确保每个实例只销毁一次。新 Client 创建失败时不得错误销毁仍在运行的旧实例，也不得对新请求静默使用不匹配的旧凭据。

#### 7.4.4 影响文件与验收证据

后续业务实现预计涉及 `RealtimeTranslationAgent.cs`、新增翻译 Client 管理器、`ServiceRegistration.cs` 和对应测试；无需为了 Client 复用重写房间语言队列或游客分发。

验收必须证明同配置连续/并发调用只创建一个 Client，英文与西班牙语请求互不串内容；取消其中一条请求不影响其他请求；轮换配置时新旧请求各自完成；Client 释放次数正确。记录 Client 创建数、在途数与请求耗时，不把减少对象创建数作为降低模型调用次数的证据。

## 8. 断线恢复与播放器

### 8.1 房主输入恢复

建立 `starting → capturing → interrupted → reconnecting → capturing/stopped` 状态，并使用会话代次隔离异步回调。

- 自动重连仅处理仍有有效讲解意图的短暂断网，候选退避为 500ms/1s/2s 加抖动；用户结束、离开、切账号、丢失播放权和权限错误不重试。
- H5 `/input` 重新握手，不发送 `input.start`；支付宝 `/events` 待订阅就绪后再按现有协议启动输入。
- 服务端上一输入轮次未完成时会拒绝新轮次。需要可判定的就绪/拒绝原因，确认旧轮次处理结束、新 epoch 已建立，不能以 WebSocket 已打开等同于可安全采音。
- 明确断线期间音频策略：首版停止采音并提示，不无界缓存；需要短缓冲续传时另行引入带采样位置、确认和幂等的输入协议。
- 麦克风权限或设备被系统撤回时提示用户重新开麦，自动重连不能恢复被撤销的权限。
- 新 epoch 清除旧重采样、VAD、去重和草稿状态；旧异步结果仍按旧 epoch 正确结清或作废，不覆盖新轮次。

### 8.2 游客播放与积压

第一版保留现有 MP3 格式。起播缓冲试验约 60～120ms，区分首次起播/断音恢复与连续排期：连续 PCM 块按 playhead 无缝连接，不给每块反复增加固定等待。

只在真实不连续、开始或主动停止处做短淡化，不能对连续 PCM 每块都淡入淡出。解码失败应报告当前片段并允许后续完整片段继续；当前房间回调会停止播放器，需要与底层错误处理一起调整。

播放队列超限策略：

- 将约 8 秒作为候选提示线，实际阈值结合目标语言的语速和自然译文长度确定；本地队列秒数不等于源讲解端到端延迟。
- 默认提示延迟并提供“跟上最新”操作；自动跳段仅在明确启用的实时模式中执行，并向用户说明遗漏。
- 跳转必须从当前可用或下一完整讲解段起播，清除旧 source、待解码任务和半片段，并提升本地播放代次、设置段号下界，阻止在途旧片段重新入队。
- 若共享语言生成也落后，重新订阅最新位置不一定立即变快；同时评估服务端语言队列年龄，不能承诺清空本地播放器即可追上现场。
- 音频事件需能关联讲解段和 TTS 子片段；只有在确认完整起点后恢复接收。单个游客跳转不取消其他游客的共享生成。
- underrun 只统计连续讲解期间、预期应有音频的断音；首次起播、车夫停顿、暂停和正常结束不计为异常。

PCM、WebCodecs 或其他流式解码列为后续能力试验。若选择 PCM，应协商每种客户端格式或提供两种输出路径，不能全局改 `RealtimeAudioFormat` 导致支付宝失声；同时量化带宽、CPU 和首音收益。

## 9. ASR 准确率与长期流式方案

### 9.1 先建立真实语料基线

录制安静室内、车流、风声、远近麦、轻声、北京口音、专名、数字/否定和中外语混说等样本，准备人工参考文本。至少覆盖 30～60 分钟、3 位说话者和 2 类真实设备，独立保留调参集与验收集。

分别计算中文 CER、适用语言的 WER、专名正确率、数字/否定错误、漏识别率、噪声误触发与重复词删除。报告 ASR 原始文本与任何后处理结果，避免后处理掩盖模型问题。

路线热词包括景点、人名、街巷和文博术语，仅在供应商支持并验证后传入；热词也要测误插入。现有 TTS 发音词典用于合成发音，不能视作 ASR 热词支持。

不增加会编造人名、否定或数字的通用“润色”步骤。确需纠错时限制为可审计的词表匹配，并保留原结果。输入时长由 PCM 样本数计算；供应商 duration、字数比和异常重复只能作为辅助指标。

近嘴麦克风与防风罩纳入硬件对照，结合已有浏览器降噪判断收益。

### 9.2 真正流式 ASR 的接入条件

长期方案为持续音频上行、临时结果修订、最终结果提交的实时识别会话。文件上传接口即使能流式返回文字，也不自动具备持续音频上行能力；供应商具体能力需按当前文档和实际账号验证。

先抽出文件分段识别与实时识别的适配边界，保持上层稳定文本提交、翻译和播放协议。候选模型用同一批录音和延迟测量比较，并验证：

- 支持的源语言、混说、热词、词时间戳、标点、临时结果撤回及最终结果语义。
- 推荐音频帧大小、会话长度、连接限制、并发配额、服务端位置、端点检测和计费方式。
- 断线后是否支持续传、确认游标和去重；不支持时建立新 epoch 并明确缺口。
- 中间结果只显示草稿，最终结果不重复提交；流式服务故障时可降级到已验证的分段方案。

此阶段与短期调优分开发版；是否替换供应商由准确率、延迟、稳定性和成本共同决定。

## 10. 支付宝与共享协议

### 10.1 支付宝采音能力

项目 `apps/mp-alipay/src/services/barge-in.js` 已探测并使用 `onFrameRecorded` 和 PCM，说明有可复用的能力检测逻辑；这不是所有设备均支持连续讲解的证明。

先在目标基础库和 iOS/Android 真机上验证 PCM 格式、采样率、帧间连续性、末帧回调、录音时长上限、与播放并用、锁屏行为。通过后复用录音占用管理，支持持续帧上传；裸 PCM 不走 WAV 解析。

保留旧 WAV 路径作为明确标注的兼容模式，测量每次 stop/start 的间隙。若某些设备达不到连续采音要求，提供 H5 讲解入口；不能仅因存在帧 API 就立即删除所有回退。

先核实 `my.sendSocketMessage` 的 `data/isBuffer` 约定，真机验证服务端收到的是 PCM 二进制以及样本值正确。现有 base64 加 `isBuffer` 不直接替换成 ArrayBuffer。

`pendingUploads` 和播放器文件数逐步改为可观测任务队列与时长指标；Promise 链不能任意“删最旧一段”。任何丢弃均走第 7 节缺口流程。保留文件数量/存储硬限制，并及时清理播完文件，不能把 240 个文件解释成固定播放秒数。

### 10.2 新事件建议

以下为待设计协议，不能直接假设旧客户端已经支持。

| 事件类别 | 建议事件 | 关键约束 |
| --- | --- | --- |
| 输入就绪 | `input.ready` | 返回新 epoch、音频格式与能力，解决打开连接和可采音不一致的问题 |
| 房主草稿 | `transcript.preview` | 独立源段号、修订号、是否稳定；仅房主接收，不改变最终段号 |
| 源音频缺失 | `segment.dropped` | 明确源段/采样范围和原因；不能当作成功提交，也不能插入虚构译文 |
| 延迟状态 | `pipeline.status` | 上行、识别、语言生成分阶段状态，节流下发，不逐帧广播 |
| 游客追赶 | 客户端播放状态或订阅确认 | 关联新的播放代次和起始完整段；区分“用户选择跳转”和“系统丢段” |

当前 `RoomEventCursor` 对 `segment.dropped` 没有显式拒绝规则，不需要为“放行未知事件”机械修改；需要新增的是收件人、订阅版本、epoch、源序号和去重语义。房主草稿不能被通用广播发给全部游客。旧客户端对未知事件的实际行为必须测试。

共享消息词典为支持的八种语言补齐网络延迟、系统暂停、内容跳过和跟上最新等提示；只展示用户能理解的状态，不展示阈值、内部 API 或实现说明。

## 11. 实施批次与影响面

| 批次 | 交付内容 | 前置条件与退出标准 |
| --- | --- | --- |
| P0 基线与稳定性 | 阶段指标、录音帧停滞检测、尾包与取消边界、现有停止/错误流程回归 | 可定位一次讲解的每阶段等待；结束无漏尾、取消不迟到重启 |
| P1 采音与切段 | Worklet 聚合、抗混叠回退、预卷、可配置 VAD/切段 | 相同语料准确率无明显下降，样本连续、无重复帧和漏帧 |
| P2 提交与队列 | 房主草稿、语言拼接、提交预算、时长队列；必要时两路 ASR | 先有元数据与有界重排，再开重叠、去重和并发；gap 不跨句 |
| P3 播放与恢复 | 完整段追赶、分阶段状态、输入就绪协议、真机自动恢复 | 两端协议联调，旧 epoch/旧片段不会回流，权限撤销仍有效 |
| P4 准确率与流式 | 热词、硬件对照、候选模型比较、流式识别试点 | 独立验收集证明收益，可回退文件分段方案 |
| LLM Client 专项 | 专用单例管理器、请求隔离、配置轮换与租约释放 | 按第 7.4 节独立交付；先验证生命周期，再验证两种语言并发及同语言多人分发，不与 VAD 调参混合 |
| 独立工程任务 | 音频模块从 demo 抽到共享包、持久化异步化 | 不与首次调参混合；按实际复用入口、性能证据和可靠性要求实施 |

共享 `PcmSpeechSegmenter`、`TranslationCommitter` 同时影响 `DuplexTranslationSession`，新参数先由房间显式传入。TTS 格式保留当前全局默认；权限、会话锁和播放权不能为追求速度被绕过。

生产音频模块抽离时同步维护 demo、H5 的导入路径、Worklet 资源 URL、构建产物及测试。后端改动会涉及另一个仓库；实施时单独检查该仓库的工作区与约束。

## 12. 验收、发布与回滚

### 12.1 指标与候选目标

先记录旧版本基线，再冻结场景、设备、网络和配置做对照。以下为第一轮目标，若供应商或设备达不到，应记录实际分布并调整方案，不能通过静默丢词或跳音频“达标”。

| 指标 | 测量口径 | 第一轮目标 |
| --- | --- | --- |
| 稳定原文延迟 | 语义单元实际说完至房主显示稳定原文，另记草稿延迟 | P50 ≤ 2 秒、P95 ≤ 4 秒；报告强切与自然停顿两类 |
| 游客首音延迟 | 同一语义单元说完至对应译音实际起播 | P50 ≤ 4 秒、P95 ≤ 7 秒，按目标语言分别报告 |
| 长时间积压 | 连续讲解 10 分钟及耐久测试，观察队列年龄趋势 | 无持续单向增长；正常网络不自动丢段，无持续累积至几十秒 |
| 非预期断音 | 连续待播内容中实际出现的播放空洞 | 相比基线显著下降，记录次数和 P95 时长，不把自然停顿计入 |
| 识别质量 | 固定验收集 CER/WER、专名、数字/否定、漏词和重复词 | 不劣于基线；任一关键事实被去重误删作为阻断项 |
| 协议正确性 | 退出、切账号、gap、重连、切语言、正常/立即结束 | 无跨 epoch 覆盖、跨 gap 拼句、乱序或旧音频恢复 |
| 成本与容量 | ASR 每分钟请求数、识别并发、LLM/TTS 调用、带宽 | 明确变化，符合账号配额和试点成本上限 |

达到阶段性能目标不代表支持任意讲话速度；对长时间译音长度超过现场讲话时长的语言组合，报告语速、自然停顿和播放追赶策略。

### 12.2 必要测试

- 切段：随机输入块边界、20ms 帧、预卷、弱起音、非整数采样率、强切回退后样本不丢、重叠、短词、纯噪声、正常结束尾包。
- 去重/提交：真实重复词、同音误识别、pending 清空后的重叠、混合语言空白、从句未完、detector 超时和截断、部分前缀后的预算、gap 与跨 epoch。
- 调度：ASR 乱序完成、首段超时、429 `Retry-After`、重试预算、队列淘汰通知、最后一段被淘汰、持久化失败与退出排空。
- 播放：MP3 半片段、PCM 连续块、解码失败后继续、追赶时在途旧片段、单个游客暂停不影响其他游客、末段正常播完、播放权切换。
- 设备：iOS Safari、Android 浏览器和支付宝真机；锁屏/切后台/恢复、权限撤回、蓝牙与有线麦克风切换、短断网和网络持续拥塞。
- 场景：城市噪声中静默、自然连续讲解、带停顿和自我纠正、两种以上目标语言、同语言多游客、讲解中加入与切语言。无需要求车夫不换气。

多语言共享生成专项验收：

- 中文房主、5 位英语游客、3 位西班牙语游客。正常无重试时每个提交段只有一轮英文生成、一轮西班牙语生成；比较业务生成任务数，不把 TTS 子片段请求算成重复生成。
- 同一英文源段的音频内容一致地分发给符合订阅起点的 5 位游客，西班牙语同理；游客不能收到另一种语言音频。
- 增加同语言游客、某位游客重连或退出，不重新生成已处理段；新游客从确认的下一完整段接入。
- 一位英语游客的发送队列变慢或播放暂停，不阻塞其余英语游客和西班牙语输出；已有语言失败不取消另一种语言。
- 保留三种活跃目标语言上限；加入第四种语言时维持现有明确拒绝行为，不顺带扩大容量。

LLM Client 复用专项验收：

- 多个作用域、多个房间并发判边界和生成英文/西班牙语，配置相同只创建一个 Client；请求消息、目标语言、选项和响应分别匹配。
- 连续多次调用后 Client 仍可用，调用结束只释放租约；取消一次翻译或提前结束流式枚举能释放对应租约，其他调用继续。
- 修改密钥、服务地址、超时或重试策略，新调用使用新 Client；旧流式请求完成前旧实例不被释放，完成后恰好释放一次。
- 并发首次获取、配置轮换、新实例创建失败和容器关闭均不泄漏实例；重复释放租约不重复销毁 Client。
- 通用工厂其他调用方的创建/释放方式保持兼容，固定 `deepseek-flash`、关闭思考及只传当前待译原文的现有测试继续通过。

### 12.3 灰度与回滚

房间专用配置分别控制切段参数、预卷/重叠、去重、提交策略、ASR 并发、草稿事件、输入自动恢复和实时丢段模式，记录配置版本。默认关闭未经验证的自动丢段与自动跳转，不保留无功能的预埋并发字段。

先发布兼容新增事件的客户端，再灰度后端能力；涉及输入就绪、重叠元数据或音频格式时显式协商能力。配置切换在新输入 epoch 或新房间生效，不在半个音频段内改变切段与去重规则。

出现漏词、重复播报、关键事实变化、撤权失效、积压失控或锁屏后静默失败时回滚对应能力。原有分段识别与 MP3 播放保留为回退路径；日志保留配置版本和失败阶段，以便区分性能变化与供应商波动。
