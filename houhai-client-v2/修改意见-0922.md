# 黄包车 AI 讲解产品 · 修改意见

**来源**：`0922.md`（产品讨论录音转录，ASR 质量较差，以下为提取整理）
**场景**：什刹海 / 鼓楼 / 烟袋斜街片区，游客上黄包车后扫码进入 AI 讲解
**整理日期**：2026-09-22

---

## 一、贯穿全局的设计原则

讨论中最重要的一条判断，后面很多改动都由它推导：

> **黄包车场景 ≠ 博物馆场景。** 博物馆里时间和空间相对自由；黄包车一旦开始就是**连续性行动**，停不下来、也退不回去。

由此派生两条：

1. **信息要做减法** —— 任何与"当前这趟车"无关的入口都是干扰
2. **交互要简单直接** —— 用户在车上不能做复杂操作

---

## 二、新增：进入前的语种与风格选择页

当前缺失，需要前置一层。

- 面向外国游客（举例日本人、俄罗斯人），进主页面前必须先选**语种**
- 选完语种后，该语种下再给 **N 个讲解风格**选项，设一个默认值
- 选完点「进入」才进主页面

---

## 三、主页面（地图页）

### 3.1 删除以下元素

判定为**信息干扰**：

| 元素 | 理由 |
|---|---|
| 顶部 Logo | 占比过大 |
| 「当前探索地」 | 用户已经在黄包车上了 |
| 「黄包车漫游 / 场馆探索」Tab | **用户已经上车，没有探索其他场馆的需求** |

搜索框可以保留。

### 3.2 新增：讲解路线列表

> 地图上虽然有顺序序号，但"依然不是一个比较有条理的东西"，容易重复和干扰。

- 做成**可横向滑动的路线卡片**（不同的讲解路线）
- **支持搜索路线**
- 选中后直接带入该条路线的讲解

### 3.3 新增：中央大按钮「开始行程」

- 放在页面中间，做大
- 点击后**主动获取定位**，进入讲解内容环节

### 3.4 点击后要跳走，不要停留

> "这个页面我已经看到了、大概知道路线了，可以随时退回来。"

点「开始行程」后应**带入行程页**，而不是固定在地图页。

---

## 四、行程页（原「导航页」）★ 改动最大

### 4.1 核心结论：不做「导航」，做「接下来看什么」

> **导航存在的意义是"你不知道怎么走"。但你跟着黄包车走，不需要导航。**

用户真正的需求是：

> "我想进入以后，首先能知道我接下来游览路线的这个地点、有什么样的展物文物。**我前面这块是鼓楼，这块是钟鼓楼**，那我大概就知道了。"

**衍生否决项：不做数字孪生。**

> "我已经在这儿了，我都能看到我周边的风景，我还要许一个虚拟的数字孪生给他对应上吗？"

2D 图上放个方向标识"功能上是 OK 的，但体验上不是最佳"。

### 4.2 页面结构

```
点「开始 / 播放 / 进入」
  ↓
AI 带着你走
  ↓
下方：看到正在行进的路径 + 途经点
同时：看到当前讲解的内容（不只是地图上的标记）
```

### 4.3 讲解内容要可视化

内容不能只有地图标记，要**简单直接**：

- 配**图片**
- 可弹出的**视频**
- **文字介绍**：放大可展开、也能收起来看走到哪了
- 跟着播放进度可浏览讲解内容

### 4.4 内容面板的具体改法（以烟袋斜街为例）

- 把**途经点**展示出来
- 讲解内容能**展开 / 收起**
- **背景换成烟袋斜街的实景背景**
- 弹窗 / 面板**扩大一倍**，放在**中间位置**，可收起
- 默认状态面板**做长一点**，至少能滑动看到介绍

### 4.5 双向切换

- 有按钮**随时退回主地图**
- 也能**随时切回**行程页

## 六、语音问答 ★ 本次讨论的主要分歧点

### 6.1 位置与交互（共识部分）

- 入口放在**行程页下方**
- **按住说话**
- 可以**打断讲解** —— "问话的优先级高于讲解"
- 问完后由 AI 判断**是否继续讲解、从哪里接着讲**
- 回答要用**对应的音调 / 用户选的那个讲解风格**

典型场景：到了鼓楼，播放了古人的音乐，再用英语讲解 —— 游客自然会问"为什么这样唱""这鼓楼背景是什么样的"。

### 6.2 技术现实（已确认的约束）

- 链路是 **语音 → 文字 → 大模型 → 文字 → 语音**，不是端到端，延迟必然大
- 要自然、要能打断、还要 follow 原本路线，本质是**全双工 agent + 上下文管理**
- 叫第三方 API **不保证实时吐出**，稳定性有风险
- 自部署要**为该用户抢占算力**，成本高
- 参照：**Kimi 自己都没有打电话功能**（现场实测确认）
- 开发成本估算：**至少 2 人 × 1 周**调试；要做好得 all in

### 6.3 三种方案，未定论

| 方案 | 支持理由 | 反对理由 |
|---|---|---|
| **A. 全语音实时对话**（可打断） | 最接近真人体验，"你就认为他是一个真人" | 成本高、延迟大、**"肯定会翻车"** |
| **B. 语音问 + 文字答** | 游客正在看风景，不想一直盯手机；成本与风险都低 | "我发语音问问题，还不如你让他打字呢，这就非常奇怪了" |
| **C. 不打断，让他讲完** | 体验最顺，"就让他都讲完" | **"那这个就跟 AI 完全没关系了"**，退化成固定讲解路线 |

### 6.4 倾向性结论

> **"我倾向于把它做成一个附加的功能，不能作为主功能，因为你肯定是会翻车的。"**

但留了一个反驳：全程不打断的话，产品就没有 AI 含量了。**这个矛盾本次没有解决。**

### 6.5 支持投入的理由（拓展性）

> 如果实时语音这块做好了，**不止黄包车** —— 可以复用到其他促进入园 / 线下文旅的各种场景，想象空间会更大。

## 七、待办 / 待调研

| # | 事项 | 说明 |
|---|---|---|
| 1 | 调研**实时语音 API** | 点名讯飞、MiniMax、OpenAI Realtime API。重点测**稳定性**，不只是有没有 |
| 2 | 核算**云端算力成本** | 显卡按时售卖的报价要查；对比自部署 vs 叫 API |
| 3 | 定**语音问答的形态** | A / B / C 三案择一，决定它是主功能还是附加功能 |
| 4 | 解决 **AI 含量的矛盾** | 若选 C（不打断），产品的 AI 价值点要重新找 |

---

## 八、排期建议

第六节那个矛盾（打断体验差 vs 不打断就没 AI）是本次讨论**没有收口**的地方；而一到五节的改动基本都是明确的、可以直接进需求。

建议：

1. **一到五节先做掉** —— 都是信息架构和交互层面的确定性改动，不依赖语音方案
2. **语音问答先按 B 方案**（语音问、文字答）做低成本版本验证
3. **并行调研 A 方案**的实时 API 稳定性

B 版本本身也能回答"游客到底会不会问问题、问什么问题"—— 这是选 A 还是选 C 的真正依据。
