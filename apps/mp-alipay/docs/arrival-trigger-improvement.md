# 近站讲解触发改进方案

## 目的与边界

当前运行配置 `routeCorrection: false`：暂时屏蔽纠偏，线段补判与近站判定改用原始定位转换后的 WGS84 坐标；纠偏算法保留，后续可通过配置恢复。

本文只处理一个问题：车（黄包车）从接近站点到讲解开始播放这一段链路的命中率与延迟。定位采集本身、路线纠偏本身不在范围内。

当前已落地第一阶段：P1-1 线段穿越判定、P1-3 坏采样容忍和 P3-1 `arrival-decision` 诊断。线段输入使用已有纠偏输出的 WGS84 位置，长度超过 120 米或样本超过 15 秒不会参与补判；弱定位或短暂定位失败最多保留 2 帧/6 秒的已累计停留。P1-2 停驻快速触发、P1-4 单候选立即入队、P1-5 音频预热和 P2 策略仍需真机数据后分阶段实施。

工程边界，改代码前先确认：

- 不缩小上报的定位精度，不把 `accuracy` 当可调参数。
- 不通过叠加误差或放大 `proximityMeters` 来"补偿"精度，那只是把误播换成漏播。
- 不引入静音音频、常驻定时器等保活手段。
- 不承诺熄屏后仍能触发。系统挂起后 `my.getLocation` 停止，这是平台约束，见 [location-validation.md](location-validation.md)。
- 判定输入仍是 WGS84 坐标加现有路线纠偏结果；纠偏不提升原始精度，也不刷新原始时间戳。

## 现状链路

一次"进圈→出声"要经过六段：

| 阶段 | 位置 | 现状 |
| --- | --- | --- |
| 1. 采样 | [location.js](../src/services/location.js):82,114 | 约 1 秒节奏，慢请求结束后至少 200ms；`type: 0`、`cacheTimeout: 0` |
| 2. 纠偏 | [index.js](../src/pages/tour/index.js):609 | `createRouteMatcher().arrival`，跳点未确认时不出点 |
| 3. 范围判定 | [tour.js](../src/core/tour.js):67-79 | 只用**当前帧**到范围的距离，`distance <= proximity` 才算接近 |
| 4. 稳定停留 | [index.js](../src/pages/tour/index.js):576-580 | 同一候选连续存在满 1.5 秒才进入稳定集合 |
| 5. 提示卡 | [index.js](../src/pages/tour/index.js):614-631 | 弹卡并倒计时 3 秒，结束后才入队 |
| 6. 入队播放 | [index.js](../src/pages/tour/index.js):628、516 | `enqueueCandidates` → `startNextSequence` → `enter` → 播放 |

时延预算（车 3 m/s，约合 11 km/h）：

| 阶段 | 现在耗时 | 车已前进 |
| --- | --- | --- |
| 进圈到命中帧 | 0.3–3s | 1–9m |
| 稳定停留 | 2–4s（需两帧） | 6–12m |
| 提示卡倒计时 | 3s | 9m |
| 入队到出声 | 0.3–2s（首次缓冲） | 1–6m |
| **合计** | **6–12s** | **17–36m** |

这就是"到站才开口"的体感来源：不是定位不够准，是判定和时序把时间花掉了。

## 判定缺口

按影响排序：

1. **单点判定**。`candidates` 每帧只算当前点到站点的距离。采样一拍跨 3–9 米时通常够用，但只要那一拍精度掉到 60 米、点被甩到 55 米外，这一站就永久错过。而 `maxAccuracyMeters` 恰好允许 65 米。
2. **坏点清零**。[index.js](../src/pages/tour/index.js):574 在候选为空时直接把 `_dwell` 置空。一次 66 米精度的点、一次短暂超时，就把已经积累了 1 秒的接近状态全部抹掉，重新计时。
3. **精度与阈值错配**。[geo-range.ts](../../../packages/ts-shared/src/geo-range.ts):49-55 里 `maxAccuracyMeters: 65` 大于 `proximityMeters: 50`。误差比阈值还大的点被判为"可用"，但它几乎不可能满足距离条件，只会污染判定。
4. **没有速度信号**。黄包车到站会停或明显减速，这是最可靠的到站证据，现在完全没用上。
5. **固定 3 秒倒计时**。单候选场景下这 3 秒没有任何决策价值，纯粹是延迟。
6. **跨站没有音频预热**。[audio.js](../src/services/audio.js):15 的 `prepareNext` 只预取当前队列的下一段，到站才开始加载首段，首次缓冲 0.3–2 秒。
7. **密集站点同时入候选**。间距小于 `releaseMeters`（默认 80 米）时多个站点同时满足接近条件，会弹多选卡，进一步增加延迟。

## 改动项

### P1-1 线段穿越判定

- 位置：[geo-range.ts](../../../packages/ts-shared/src/geo-range.ts):276，[tour.js](../src/core/tour.js):75
- 现状：只用当前点到范围的距离。
- 改动：把已有的 `distanceToSegmentMeters` 导出，对"上一帧→当前帧"的线段求到站点范围的最短距离，取 `min(点距, 线段距)` 参与接近判定。
- 依据：车经过站点的物理事实是一段轨迹穿过范围，不是某一帧恰好落在圈内。判定半径不变，只是不再漏掉帧间穿越。
- 范围类型差异：
  - 点：线段到锚点距离。
  - 圆：`max(0, 线段到圆心距离 - radiusMeters)`。
  - 多边形：线段与任一边相交，或任一端点在多边形内，即视为穿过；否则沿用点到边界距离。
- 风险：相邻两帧跨度过大时，线段可能"扫过"本不该命的站点。用帧间隔上限（`maxAgeMs` 已有的 15 秒）和线段长度上限（建议 120 米）排除。
- 验收：单帧精度 60 米、真实横向偏移 10 米的场景，仍能命中。

### P1-2 停驻触发

- 位置：[tour.js](../src/core/tour.js):74，[index.js](../src/pages/tour/index.js):576
- 现状：只有 `approaching`（距离减小）一个信号。
- 改动：用相邻两帧计算速度 `speed = metersBetween(previous, current) / dt`。当 `speed < 0.8 m/s` 且距离 `<= proximityMeters × 1.4` 时，视为已到站，跳过 1.5 秒停留等待，直接进入稳定集合。
- 依据：低速停驻是行为证据，不是误差补偿，不违反精度口径。它解决"车停在站旁、GPS 偏到 55–70 米"的典型漏播。
- 风险：堵车、等红灯时的低速可能误判。用"距离在 1.4 倍阈值内"和"该站未完成"两道限制收敛；车速阈值不要高于 1.0。
- 验收：停车位置与站点真实距离 55 米、定位误差 25 米时，10 秒内触发。

### P1-3 坏采样容忍

- 位置：[index.js](../src/pages/tour/index.js):574
- 现状：候选为空即清空 `_dwell`。
- 改动：改为窗口容忍。记录每个候选的首次命中时间 `firstSeenAt`；中间允许 1–2 帧丢失，只要累计跨度满 `dwellMs`、最后一次命中在 `maxAgeMs` 内，就仍然稳定。
- 依据：单帧坏点不应推翻已观察到的接近过程。这与"弱定位不触发到站"不冲突——触发时仍然要求当前帧通过 `isUsableLocation`。
- 风险：容忍窗口过长会让已经离开的站点继续保持稳定状态。建议容忍上限 2 帧或 6 秒，取先到者。
- 验收：人为注入一个 70 米精度点，确认后续正常点仍能触发，且不出现误播。

### P1-4 单候选取消倒计时

- 位置：[index.js](../src/pages/tour/index.js):617
- 现状：`deadline = Date.now() + 3000`，倒计时结束才入队。
- 改动：`visible.length === 1` 时立即入队播放，提示卡改为"已开始讲解 · 取消"的可撤销条，保留 3 秒可取消窗口但不阻塞播放；`visible.length > 1` 时保留倒计时（建议缩到 1.5 秒）让用户选择。
- 依据：单候选时倒计时不产生任何决策，只产生延迟。
- 风险：用户想先看完当前站再听下一站时会被打断。撤销条和"手动暂停后不再自动切站"的现有规则可以覆盖。
- 验收：进圈到出声不超过 3 秒。

### P1-5 跨站音频预热

- 位置：[index.js](../src/pages/tour/index.js):573，[audio.js](../src/services/audio.js):15
- 现状：`prepareNext` 只覆盖当前队列的下一条。
- 改动：当某站距离进入 150 米，且该站尚未播过时，预热它的首段音频：复用 `createInnerAudioContext` 预置 `src` 并保持 `autoplay = false`，或对远端 URL 先 `my.downloadFile`。同一时刻只保留一个跨站预热实例，距离回升到 150 米外即释放。
- 依据：首次缓冲是纯网络时间，与判定无关，完全可以提前做掉。
- 风险：并发预热会挤占音频通道。必须与当前播放实例互斥，播放中不预热。
- 验收：触发到出声的音频部分不超过 300ms。

### P2-1 精度与阈值错配

- 位置：[geo-range.ts](../../../packages/ts-shared/src/geo-range.ts):54
- 现状：`maxAccuracyMeters: 65` 大于默认 `proximityMeters: 50`。
- 改动：二选一，倾向方案 B。
  - A：把 `maxAccuracyMeters` 收敛到 50，接受更少的有效样本。
  - B：保留 65，但对 `accuracy > proximityMeters` 的帧，距离判定降级为"不可用"，只允许线段穿越与停驻这两条强信号路径命中。
- 依据：误差大于判定半径时，距离这个数字本身没有判别力。
- 风险：B 会让高误差环境下可用帧变少，需要真机确认触发率。
- 验收：在 55–65 米精度区间，不再出现"稳定但不触发"和"稳定但乱触发"两种极端。

### P2-2 密集站点只取顺序下一站

- 位置：[tour.js](../src/core/tour.js):78
- 现状：所有未完成且进入阈值的站点同时进入候选。
- 改动：当两个站点间距小于 `releaseMeters × 2` 时，只保留 `order` 靠前的一个，其余延后到前一站完成后再参与。单向线路默认按 `order` 推进。
- 依据：避免同屏多候选导致的选择延迟和误选。
- 风险：线路折返、站点分列两侧时可能压制正确站点。用"当前站点之后的第一个未完成站"作为优先项，折返线路需单独配置。
- 验收：间距 60 米的两站，全程只弹一次单选提示。

### P3-1 决策埋点

- 位置：[diag.js](../src/services/diag.js) 调用点，[index.js](../src/pages/tour/index.js):573
- 内容：新增 `arrival-decision`，字段为 `{ spotId, distance, accuracy, speed, source, dwellMs, latencyMs }`，其中 `source` 取 `point | segment | stop`，`latencyMs` 为首次进圈到入队的耗时。
- 约束：不记录经纬度，不持久化轨迹，不上传，与现有诊断口径一致。
- 用途：没有这组数据，无法判断改动是否有效，也无法区分"漏播"与"播得晚"。

### P3-2 测试

- 位置：[circle-arrival.test.cjs](../tests/circle-arrival.test.cjs)
- 用例：
  - 两帧分别在阈值外，线段穿过范围 → 命中。
  - 两帧都在阈值外且线段不穿过 → 不命中。
  - 单帧 70 米精度 → 不污染已有稳定状态。
  - 停驻帧（速度 0.3、距离 1.3 倍阈值）→ 命中。
  - 密集站点两站同时进阈值 → 只返回一个候选。
  - 同一站点重复命中 → 不重复入队。

## 参数

| 参数 | 现值 | 建议 | 说明 |
| --- | --- | --- | --- |
| `proximityMeters` | 50 | 不变 | 站点或范围配置可覆盖，不靠放大它提升命中率 |
| `releaseMeters` | 80 | 不变 | 与站点间距的关系由 P2-2 处理 |
| `dwellMs` | 1500 | 1500（仅纯距离路径生效） | 穿越与停驻走快速通道，不等停留 |
| `maxAccuracyMeters` | 65 | 65，叠加 P2-1 方案 B | 高误差帧只允许强信号命中 |
| 停驻速度阈值 | 无 | 0.8 m/s | 高于 1.0 会把正常慢行误判为到站 |
| 停驻距离系数 | 无 | 1.4 × proximity | 与低速配合，避免路口误判 |
| 线段长度上限 | 无 | 120 m | 防止跨度过大的线段误扫 |
| 坏采样容忍 | 0 | 2 帧或 6 秒 | 超出即清空稳定状态 |

## 上线顺序

1. P1-3 坏采样容忍（改动最小，先止住"莫名其妙清零"）。
2. P1-1 线段穿越（消除主要漏播）。
3. P1-4 取消单候选倒计时（用户可感知的提升）。
4. P1-2 停驻触发。
5. P1-5 音频预热。
6. P2 两项在真机数据支持后再动。

每步单独提交，独立可回滚。P3-1 的埋点建议和第一步一起进，便于前后对比。

## 验收

沿用 [location-validation.md](location-validation.md) 的真车流程，增加三项记录：

| 指标 | 采集方式 | 目标 |
| --- | --- | --- |
| 进圈到出声 | `arrival-decision.latencyMs` | 中位数 ≤ 3s |
| 站点命中率 | 实际触发数 / 经过站点数 | ≥ 95%（亮屏、正常精度） |
| 误播次数 | 非相邻站点被触发 | 0 |

亮屏、定位精度 ≤ 50 米是这套指标的成立前提；超出该前提的场景只记录，不设目标。

## 不做

- 不通过上报更小的 `accuracy`、叠加误差或放大阈值来提升命中率。
- 不用静音音频或常驻定时器维持后台运行。
- 不把本方案描述为"已支持熄屏持续定位"。息屏后能否触发仍取决于系统是否继续向支付宝提供位置，需按 [location-validation.md](location-validation.md) 的真机结论表述。
