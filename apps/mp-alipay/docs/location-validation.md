# 路线匹配与熄屏定位实测

## 判定口径

- 地图显示、跟随和回中使用连续轨迹匹配结果。
- 圆形/多边形范围、接近距离、稳定停留和到站触发在匹配成功时使用纠偏后的定位；将地图上的 GCJ-02 匹配结果转换为 WGS84 后判断。不再要求原始坐标同时进入范围。
- 匹配不确定、失配或缺失路线时，使用原始 WGS84 定位判断。无论采用哪种坐标，定位精度、有效期和稳定停留要求都保留；纠偏不提升原始精度、不刷新原始时间戳，原始测量仍单独保留。
- 路线几何使用 GCJ-02 建图；景区边界不作为道路；只有共享顶点才视为连通。相交但没有共享顶点的两段几何不自动连通。
- 匹配使用已有配置路线，不需要部署路网服务。若现场需要匹配路线外道路，另行评估 Valhalla pedestrian 和目标区域的道路覆盖。

## 连续匹配验证

选择含平行巷道、交叉口、折返和真实拐角的路线，开启附近讲解并步行或乘车经过：

1. 沿当前路段前进，观察轻微定位抖动是否跳到平行路或折返路段。
2. 在真实拐角转向，确认匹配能通过共享顶点转入下一段；沿原路折返时应允许反向移动。
3. 暂时离开配置路线，确认失配时显示原始位置，不把远处位置拉回路线。
4. 进入定位较差区域，再恢复定位，确认不会用旧轨迹约束新位置。
5. 用原始定位轻微漂离、但匹配点位于景点范围内的场景，确认经过稳定停留后能触发；匹配点位于范围外时，即使原始位置在范围内也不触发。匹配存在歧义、定位质量不足或过期时，确认执行回退或取消提示。

## 支付宝能力核对

在该应用的支付宝开放平台控制台核对是否提供专用连续/后台定位能力、适用类目、准入要求、接口文档和允许的客户端版本。公开类型声明没有列出接口不能替代控制台核对。

运行时能力日志仅报告属性是否存在。不得据此推断接口已授权、调用可成功或系统锁屏后仍提供位置。未取得平台文档与准入证明时，保持现有 getLocation 轮询与前台恢复策略。

## Android / iPhone 锁屏实测

两种系统分别使用真机和实际分发形态测试，记录系统版本、支付宝版本、基础库版本、网络及省电设置。不要用模拟器或单元测试替代。

1. 开启 `config.diagnostics`，在支付宝开发者工具 Console 过滤 `[diag] location-`；确认真机调试方式能够保留后台日志。调试连接可能影响后台行为，应在实际分发形态再次复测。
2. 前台开启附近讲解，先观察 30 秒定位，记录 `location-fix` 的 `requestMs`、`intervalMs` 和 `accuracy`。
3. 记录手工熄屏时间与位置，锁屏行走至少 3 分钟，途中经过一个尚未触发的站点，记录实际到站时间及是否听到该站讲解；同时做一次没有音频播放的锁屏测试。
4. 唤醒后查看 `location-lifecycle` 与 `location-fix`：是否在后台持续收到回调，是否只在恢复前台后收到位置，后台最大回调间隔是多少。
5. 验证返回前台立即发起新定位，旧请求的迟到响应不会覆盖新状态；定位中断超过 15 秒后应重新稳定停留再触发。
6. 单独测试切到其他应用、断网后恢复、系统省电模式，以及拒绝定位权限。记录现象，不预设这些场景能持续采集。

定位诊断不包含经纬度，不保存或上传轨迹。`location-lifecycle` 记录应用前后台变化，不代表操作系统确认了熄屏；锁屏时间需要现场记录。应用后台与导览页隐藏也不是同一个状态：在支付宝内切页不能作为系统锁屏测试。
